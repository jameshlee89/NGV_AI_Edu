# 아키텍처 설계자

이 스킬은 소프트웨어(및 필요 시 시스템) 아키텍처를 설계하고 회사 지정 양식으로 아키텍처 설계서를
작성하는 절차와 규칙을 제공한다. 목표는 다음 요건을 모두 만족하는 아키텍처 산출물을 만드는 것이다.

1. 지정된 템플릿(TPL-SWE2-001, TPL-SWE2-002) 준수
2. A-SPICE(SWE.2) · ISO 26262 Part 6 아키텍처 설계 원칙 준수
3. 높은 응집도 · 낮은 결합도
4. 변경에 유연하게 대응 가능한 구조
5. SOLID 원칙 준수
6. 컴포넌트 인터페이스를 반드시 정의하고, 컴포넌트 사이는 인터페이스로만 통신
7. 컴포넌트 통합 순서 정의
8. 후보 아키텍처 구조를 사용자에게 먼저 제안하고, 사용자가 선정한 뒤에 상세 설계로 진행

## 적용 범위와 인접 스킬과의 경계

이 스킬은 **SW 아키텍처 설계(A-SPICE SWE.2)**만 다룬다. 요구사항 도출/명세는 `requirements-analyst`,
모듈·함수 수준 상세설계는 `detailed-design`, 구현(TDD)은 `tdd`, 아키텍처 인터페이스 기반 통합시험은
`integration-testing`, 요구사항 기반 블랙박스 시스템 시험은 `sw-system-test` 스킬이 담당하며 이
스킬은 다루지 않는다.

## 0. 시작할 때 항상 할 일

1. `references/template-source.md`를 읽는다. 회사 지정 아키텍처 설계서 템플릿(TPL-SWE2-001 docx,
   TPL-SWE2-002 drawio)이 이미 저장소에 있으므로, 이 SKILL.md의 장 구성을 그대로 목차로 사용해 작성한다.
   템플릿이 갱신되거나 다른 경로로 교체되면 그쪽을 우선한다.
2. 입력 요구사항 문서(예: SW 요구사항 명세서, `requirements-analyst` 스킬 산출물), 상위 시스템 설계,
   기존 아키텍처 자산이 있으면 먼저 읽는다.
3. 대상 범위(제품/컴포넌트), 안전 관련 여부(ISO 26262 ASIL 대상인지, Safety Goal/ASIL 정보가 있는지)가
   불명확하면 먼저 사용자에게 확인한다.
4. **후보 아키텍처 구조를 사용자에게 제안하고 선택을 기다린다** — §2를 실행하기 전에는 상세 설계(§4
   이후)로 진행하지 않는다.

정보로 채운다.

## 2. 후보 아키텍처 구조 제안 및 사용자 선정 (필수 선행 단계)

`references/architecture-styles.md`의 스타일 카탈로그를 참고하여, 대상 시스템의 특성(실시간성,
안전 등급, 변경 빈도가 높은 영역, 배포 형태 등)에 맞는 후보 아키텍처 스타일을 **2~4개** 골라 다음을
함께 제시한다.

- 스타일 이름과 핵심 개념
- 이 문제에 적용했을 때의 장점 (특히 §3 응집도/결합도/변경 유연성 관점)
- 단점/트레이드오프
- ISO 26262 안전 관련 항목이 있다면 오류 격리·안전 상태 구현 관점에서의 적합성

사용자가 하나를 선정하기 전까지는 §4 이후 상세 설계(컴포넌트 분해, 인터페이스 명세 등)를 확정하지
않는다. 사용자가 명시적으로 선택하거나 조합/변형을 지시하면 그 결정을 §3 이후 설계의 전제로 삼는다.

## 3. 아키텍처 설계 원칙 (A-SPICE · ISO 26262 Part 6 · SOLID)

`references/solid-cohesion-coupling-checklist.md`에 상세 체크리스트가 있다. 핵심 규칙:

- **분해(decomposition)**: 시스템을 계층적으로 분해하고, 각 요소의 크기와 복잡도를 관리 가능한 수준으로
  제한한다.
- **높은 응집도**: 한 컴포넌트 안의 책임은 하나의 명확한 목적에 집중한다(단일 책임 원칙과 직결).
- **낮은 결합도**: 컴포넌트 간 의존은 최소화하고, 의존이 필요하면 반드시 인터페이스를 통해서만
  연결한다(§5).
- **변경 유연성**: 요구사항/기능 변경이 예상되는 지점을 식별하고, 개방-폐쇄 원칙에 따라 확장은 열려
  있고 기존 코드 수정은 최소화되도록 경계를 설계한다.
- **SOLID 5원칙**을 컴포넌트/인터페이스 설계 전반에 적용한다 — 단일 책임(SRP), 개방-폐쇄(OCP), 리스코프
  치환(LSP), 인터페이스 분리(ISP), 의존성 역전(DIP). 각 원칙의 적용 지점과 체크 방법은
  `references/solid-cohesion-coupling-checklist.md` 참고.
- **오류 격리**: 한 요소의 오류가 다른 요소로 전파되지 않도록 경계와 방어 로직을 설계한다(ISO 26262
  안전 관련 요소는 §7 참고).
- ISO 26262 Part 6의 정확한 절 번호·원문 인용이 필요한 경우, 이 스킬의 요약만으로 단정하지 말고
  `references/iso26262-aspice-architecture-checklist.md`의 안내에 따라 프로젝트에 첨부된 공식 표준
  문서를 함께 확인한다.

## 4. 논리 아키텍처 · 컴포넌트 · 정적 의존성

- 선정된 아키텍처 스타일(§2)에 따라 시스템을 컴포넌트/계층으로 분해하고, 각 컴포넌트에 ID(예:
  `ARC-XXX`)와 명칭, 목적, 책임을 부여한다.
- 컴포넌트 간 관계(허용된 의존 방향, 호출 관계, 공유 자원)를 정의하고, `references/
  solid-cohesion-coupling-checklist.md`의 결합도 체크리스트로 불필요한 결합을 제거한다.
- **정적 의존성 그래프에 순환 의존이 없어야 한다.** 순환이 발견되면 인터페이스 분리(ISP)나 의존성
  역전(DIP)으로 해소한다. 해소할 수 없으면 설계 결함으로 명시하고 대안을 제시한다.
- 로직/구조는 PlantUML(`.puml`) 컴포넌트 다이어그램으로 초안을 작성해 빠르게 검토한 뒤, 최종 산출물은
  §9에 따라 TPL-SWE2-002 drawio 구조로 정리한다.

## 5. 인터페이스 명세 — 컴포넌트는 반드시 인터페이스로만 통신

`references/interface-spec-guide.md`에 상세 규칙과 표 형식이 있다. 핵심 규칙:

- **모든 컴포넌트 간 통신 경로는 명명된 인터페이스(ID 부여, 예: `IF-XXX`)로 정의되어야 한다.** 설계
  문서나 다이어그램에 인터페이스 없이 컴포넌트를 직접 연결하는 화살표/의존을 남기지 않는다.
- 인터페이스마다 최소 다음을 명세한다: 제공자(provider) 컴포넌트, 사용자(consumer) 컴포넌트, 제공
  기능/데이터, 호출 조건(사전/사후조건), 시간 제약(해당 시), 오류 계약(오류 발생 시 반환/전파 방식).
- 내부 인터페이스(컴포넌트 간 API/이벤트/데이터 저장소)와 외부 인터페이스(하드웨어/통신/사용자/외부
  서비스 경계)를 구분해서 작성한다(템플릿 6.1/6.2).
- 인터페이스는 인터페이스 분리 원칙(ISP)에 따라 사용자별로 필요한 범위만 노출하도록 분리한다 — 하나의
  거대한 인터페이스에 서로 다른 사용자의 요구를 모두 담지 않는다.

## 6. 통합 전략 및 순서 정의

`references/integration-order-guide.md`에 상세 절차가 있다. 핵심 규칙:

- 정적 의존성 그래프(§4)를 기반으로 통합 순서를 **의존성이 없는(또는 적은) 컴포넌트부터 의존하는
  컴포넌트 순으로** 위상 정렬해 정의한다.
- 각 통합 단계마다 다음을 명시한다: 이번 단계에 통합되는 컴포넌트, 아직 구현되지 않은 의존 대상에
  필요한 스텁/드라이버, 이 단계에서 검증할 인터페이스/시나리오, 회귀 확인 범위.
- 통합 순서는 "나중에 정의"로 미루지 않고, 아키텍처 설계와 같은 작업에서 함께 확정한다(템플릿 11장).
- 안전 관련(ASIL) 컴포넌트가 있으면, 오류 격리 메커니즘이 실제로 동작하는지 확인 가능한 시점을 통합
  순서에 명시적으로 포함한다.

## 7. 동적 동작 · 상태 전이 · 오류 격리와 안전 동작

- 주요 시나리오는 시퀀스 다이어그램(PlantUML)으로 호출 순서와 인터페이스 사용을 표현한다(템플릿 7장).
- 상태를 갖는 컴포넌트는 상태, 진입/종료 조건, 전이 이벤트, 가드, 금지 전이를 상태 다이어그램으로
  정의한다(템플릿 8장).
- ISO 26262 안전 관련 요소는 오류 감지 위치, 전파 차단 지점, 안전 상태 정의, 복구/진단 정보 제공
  책임을 명시한다(템플릿 9장). 정확한 ASIL별 요구 수준은 `references/
  iso26262-aspice-architecture-checklist.md`와 프로젝트의 공식 안전 분석 문서를 함께 확인한다.

## 8. 요구사항 할당 및 추적성

- SW 요구사항(예: `requirements-analyst` 스킬 산출물의 `SWR-XXX`)을 아키텍처 요소(`ARC-XXX`)와
  인터페이스(`IF-XXX`)에 할당한다(템플릿 12장).
- 할당 누락(어떤 요구사항도 커버하지 못하는 아키텍처 요소가 없는지, 어떤 요소로도 할당되지 않은
  요구사항이 없는지)과 중복 할당을 점검한다.
- 프로젝트에 추적성 매트릭스(`requirements-analyst` 스킬의 `references/traceability-matrix.md` 등)가
  있으면, 아키텍처 요소·인터페이스 ID를 같은 작업 안에서 함께 갱신한다(템플릿 14장). "나중에 갱신"은
  허용하지 않는다.

## 9. 다이어그램 작성 규칙

- 설계 중 빠른 검토용으로 PlantUML(`.puml`) 컴포넌트/시퀀스/상태 다이어그램을 먼저 작성한다.
- 공식 베이스라인 산출물은 회사 지정 `TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio`를 복사해 사용하고,
  다음을 반드시 포함한다: 소프트웨어 요소와 계층, 제공(provided)/요구(required) 인터페이스, 허용된
  의존 방향, 요구사항 할당 ID. 안내 도형(플레이스홀더)은 실제 요소로 교체하고 남겨두지 않는다.
- 두 다이어그램(PlantUML 초안과 drawio 최종본)의 요소·관계는 항상 일치해야 한다.

## 10. 산출물 저장 및 파일명 규칙

- 아키텍처 설계서(TPL-SWE2-001)와 UML(TPL-SWE2-002)을 실제로 작성할 때는
  `WP_Templates/Engineering/SoftwareArchitecturalDesign/`의 원본 템플릿을 복사한 뒤, `WP_Templates/
  Engineering/README.md`의 규칙대로 파일명을 `<산출물 ID>_<산출물명>.<확장자>` 형식으로 바꾸고
  프로젝트/베이스라인 정보를 채운다. 저장 위치를 사용자가 지정하지 않았다면 어디에 저장할지 먼저
  확인한다.
- 템플릿 ID·적용 산출물·실제 파일 위치는 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`에
  기록되어 있으므로, 새 산출물을 등록해야 하는지 사용자에게 확인한다.

## 11. 최종 자체 검토 체크리스트

산출물을 마무리하기 전에 다음을 점검한다.

- [ ] 후보 아키텍처 스타일을 제시하고 사용자가 선정했는가 (§2)
- [ ] 모든 컴포넌트가 단일하고 명확한 책임을 갖는가 (응집도/SRP)
- [ ] 컴포넌트 간 통신이 예외 없이 정의된 인터페이스를 통해서만 이루어지는가 (§5)
- [ ] 정적 의존성 그래프에 순환 의존이 없는가 (§4)
- [ ] OCP/LSP/ISP/DIP 위반 사례가 없는가 (`references/solid-cohesion-coupling-checklist.md`)
- [ ] 컴포넌트 통합 순서가 의존관계 기반으로 명시적으로 정의되었는가 (§6)
- [ ] 모든 SW 요구사항이 아키텍처 요소/인터페이스에 할당되었는가, 고아 요구사항/근거 없는 요소가
      없는가 (§8)
- [ ] PlantUML 초안과 TPL-SWE2-002 drawio 최종본의 내용이 일치하는가 (§9)
- [ ] ISO 26262/A-SPICE 조항을 원문 확인 없이 단정적으로 인용하지 않았는가
