# 통합 순서 정의 가이드

SKILL.md §6(통합 전략 및 순서 정의)에서 사용한다. TPL-SWE2-001 템플릿 11장(통합 전략)에 대응한다.

## 1. 기본 원칙

- 통합 순서는 §4에서 정의한 **정적 의존성 그래프**를 기반으로 결정한다. 의존관계 없이 임의의 순서를
  정하지 않는다.
- 순환 의존이 있으면 통합 순서를 정의할 수 없으므로, 통합 순서를 정의하기 전에 §4의 순환 의존 해소를
  먼저 완료한다.
- 통합 순서는 아키텍처 설계와 같은 작업 안에서 함께 확정한다 — "구현 후에 정하겠다"로 미루지 않는다.

## 2. 순서 결정 절차

1. 정적 의존성 그래프에서 **의존을 받는 쪽(다른 컴포넌트에 의존하지 않는 리프/기반 컴포넌트)**부터
   시작점으로 삼는다.
2. 의존 그래프를 위상 정렬(topological sort)하여, 어떤 컴포넌트든 자신이 의존하는 컴포넌트보다 먼저
   통합되지 않도록 순서를 정한다.
3. 병렬로 통합 가능한 컴포넌트(서로 의존하지 않는 컴포넌트들)는 같은 단계로 묶어도 된다.
4. 안전 관련(ASIL) 컴포넌트가 있으면, 그 오류 격리/안전 동작(§7)이 실제로 검증 가능한 시점을 통합
   순서에 명시적으로 포함한다(너무 늦은 단계에 몰아넣지 않는다).

## 3. 전략 선택 (프로젝트 상황에 맞게 선택하고 이유를 기록)

- **상향식(Bottom-Up)**: 기반 컴포넌트부터 통합. 하위 계층이 안정적일 때 유리하며, 상위 컴포넌트
  통합 전까지 드라이버(테스트 하네스)가 필요하다.
- **하향식(Top-Down)**: 상위(정책/제어) 컴포넌트부터 통합. 조기에 전체 흐름을 검증할 수 있으나, 하위
  구현이 준비되기 전까지 스텁이 많이 필요하다.
- **샌드위치/혼합(Sandwich)**: 상/하위를 동시에 진행하고 중간에서 만나는 방식. 상위/하위가 모두
  변경 위험이 있을 때 고려한다.

## 4. 각 통합 단계에 명시할 항목

| 항목 | 설명 |
|---|---|
| 단계 번호 | 순서 |
| 통합 대상 컴포넌트 | 이번 단계에서 실제 구현체로 통합되는 컴포넌트(`ARC-XXX`) |
| 필요한 스텁/드라이버 | 아직 통합되지 않은 의존 대상을 대신할 임시 구현 |
| 검증 대상 인터페이스 | 이번 단계에서 실제로 확인할 인터페이스(`IF-XXX`)와 시나리오 |
| 회귀 범위 | 이전 단계까지 통합된 컴포넌트 중 영향을 받을 수 있는 범위 |
| 완료 기준 | 다음 단계로 진행하기 위한 통과 조건 |

## 5. 자체 점검

- [ ] 모든 컴포넌트가 통합 순서표에 정확히 한 번씩 등장하는가? (누락/중복 없음)
- [ ] 어떤 컴포넌트도 자신이 의존하는 컴포넌트보다 먼저 등장하지 않는가?
- [ ] 안전 관련 컴포넌트의 오류 격리 메커니즘이 검증 가능한 단계가 명시되어 있는가?
- [ ] 각 단계에 스텁/드라이버 필요 여부가 빠짐없이 기재되어 있는가?
