# SOLID · 응집도 · 결합도 · 변경 유연성 체크리스트

SKILL.md §3(아키텍처 설계 원칙)과 §11(최종 자체 검토)에서 사용한다. 컴포넌트/인터페이스를 정의할
때마다 아래 항목으로 자체 점검한다.

## 1. 높은 응집도 (High Cohesion)

- [ ] 컴포넌트 안의 모든 기능이 하나의 명확한 목적/책임과 관련되어 있는가?
- [ ] 서로 관련 없는 책임(예: "데이터 저장"과 "사용자 알림 발송")이 한 컴포넌트에 섞여 있지 않은가?
- [ ] 컴포넌트 이름만으로 그 책임이 명확히 설명되는가? (설명이 "그리고"로 여러 개 이어지면 응집도
      의심)

## 2. 낮은 결합도 (Low Coupling)

- [ ] 컴포넌트 간 의존 개수가 필요 최소한인가?
- [ ] 의존이 구체 구현이 아니라 인터페이스(추상)를 향하는가? (§5 인터페이스 명세와 직결)
- [ ] 한 컴포넌트의 내부 구현 변경이 다른 컴포넌트의 코드 변경을 강제하지 않는가?
- [ ] 정적 의존성 그래프에 순환 의존이 없는가? (있으면 인터페이스 분리/의존성 역전으로 해소)
- [ ] 컴포넌트 간에 전역 상태나 공유 가변 데이터를 인터페이스 없이 직접 공유하지 않는가?

## 3. 변경 유연성 (Flexibility to Change)

- [ ] 변경이 예상되는 지점(요구사항 변동성이 큰 영역, 외부 인터페이스, 파생 모델별 차이)이 식별되어
      있는가?
- [ ] 그 지점이 하나의 컴포넌트/인터페이스 경계 안에 격리되어 있어, 변경 시 다른 컴포넌트에 영향을
      주지 않는가?
- [ ] 새 기능 추가 시 기존 컴포넌트 수정보다 새 컴포넌트/구현체 추가로 대응할 수 있는 구조인가?
      (OCP와 직결)

## 4. SOLID 5원칙 적용 체크

### SRP — 단일 책임 원칙
- [ ] 컴포넌트가 변경되어야 할 이유가 한 가지뿐인가? (여러 이해관계자/여러 요구사항 출처가 한
      컴포넌트를 각자 다른 이유로 바꾸게 만들지 않는가)

### OCP — 개방-폐쇄 원칙
- [ ] 새로운 동작(예: 새 파생 모델의 옵션, 새 통신 프로토콜)을 추가할 때 기존 컴포넌트를 수정하지
      않고 새 구현체를 추가하는 것으로 대응 가능한가?
- [ ] 확장 지점이 인터페이스로 명시되어 있는가? (막연히 "나중에 확장 가능"이라고만 서술하지 않음)

### LSP — 리스코프 치환 원칙
- [ ] 같은 인터페이스의 서로 다른 구현체(예: 실제 하드웨어 어댑터 vs 테스트용 스텁)를 교체해도
      호출자 쪽 동작 계약(사전조건 강화 금지, 사후조건 약화 금지)이 깨지지 않는가?

### ISP — 인터페이스 분리 원칙
- [ ] 하나의 인터페이스에 서로 다른 사용자(consumer)가 필요로 하지 않는 기능까지 억지로 묶여 있지
      않은가?
- [ ] 사용자별로 실제 필요한 기능만 노출하는 더 작은 인터페이스로 나눌 수 있는가?

### DIP — 의존성 역전 원칙
- [ ] 상위(정책/도메인) 컴포넌트가 하위(구현 세부사항, 하드웨어, 외부 시스템) 컴포넌트의 구체 타입에
      직접 의존하지 않고, 둘 다 인터페이스(추상)에 의존하는가?
- [ ] 의존 방향이 "구체 → 추상"이 아니라 "구체가 추상을 구현"하는 방향인가?

## 5. ISO 26262 Part 6 아키텍처 설계 원칙과의 연결 (요약 — 원문 대조 필요)

ISO 26262 Part 6은 소프트웨어 아키텍처 설계에서 계층적 구조, 요소 크기/복잡도 제한, 높은 응집도,
낮은 결합도, 적절한 수준의 세분화, 불필요한 복잡도 회피, 명확히 정의된 인터페이스 등을 요구 원칙으로
다룬다. 이 체크리스트의 §1~§4가 그 요건을 구체적인 점검 항목으로 옮긴 것이다. 다만 **정확한 절/표
번호와 원문 문구는 이 요약만으로 단정하지 말고**,
`references/iso26262-aspice-architecture-checklist.md`의 안내에 따라 프로젝트에 첨부된 공식 ISO 26262
문서를 함께 확인한다(컴플라이언스 문서에 부정확한 원문 인용을 남기지 않기 위함).
