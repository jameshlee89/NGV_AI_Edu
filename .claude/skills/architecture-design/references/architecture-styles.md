# 후보 아키텍처 스타일 카탈로그

SKILL.md §2(후보 아키텍처 구조 제안)에서 사용한다. 대상 시스템 특성에 맞는 2~4개를 골라 장단점과 함께
사용자에게 제시하고, 사용자가 선정한 뒤에만 상세 설계로 진행한다. 아래는 자동차 SW에서 자주 쓰이는
스타일과 선택 기준이다 — 목록에 없는 스타일이 더 적합하면 추가해도 된다.

## 1. 계층형 아키텍처 (Layered)

- 개념: 상위 계층은 하위 계층에만 의존하도록 수직으로 계층을 나눈다(예: 응용/서비스/플랫폼 추상화/
  드라이버).
- 강점: 구조가 단순하고 이해하기 쉬우며, 계층 경계가 곧 인터페이스 경계가 되어 결합도 관리가 쉽다.
  A-SPICE/ISO 26262 문서화(계층별 책임 분리)와 궁합이 좋다.
- 약점: 계층을 관통하는 횡단 관심사(로깅, 진단)가 있으면 계층 규율이 깨지기 쉽다. 계층이 많아지면
  성능(호출 오버헤드)에 영향을 줄 수 있다.
- 적합한 경우: 플랫폼/HAL 위에 서비스가 올라가는 임베디드 SW, 명확한 상하위 관계가 있는 시스템.

## 2. 헥사고날 / 포트-어댑터 (Hexagonal, Ports & Adapters)

- 개념: 핵심 도메인 로직을 중심에 두고, 외부(하드웨어, 통신, UI 등)와의 연결은 포트(인터페이스)와
  어댑터로만 이루어지게 한다.
- 강점: 의존성 역전(DIP)을 구조적으로 강제해 결합도가 매우 낮다. 외부 인터페이스(통신 프로토콜,
  하드웨어)가 자주 바뀌거나, 테스트 시 하드웨어를 스텁/목으로 대체해야 하는 경우에 유리하다.
- 약점: 포트/어댑터 계층이 늘어나 초기 설계 비용이 크고, 팀이 익숙하지 않으면 과도한 추상화로
  오해될 수 있다.
- 적합한 경우: 도메인 로직은 안정적인데 외부 인터페이스(차량 통신, 진단 프로토콜, 센서)가 다양하거나
  변경 빈도가 높은 시스템.

## 3. 마이크로커널 / 플러그인 (Microkernel, Plug-in)

- 개념: 최소 핵심(커널)과, 커널이 정의한 인터페이스를 구현하는 플러그인(확장 기능)으로 구성한다.
- 강점: 개방-폐쇄 원칙(OCP)을 구조로 실현한다 — 새 기능 추가 시 핵심을 수정하지 않고 플러그인만
  추가한다. 기능 변형(옵션/파생 모델)이 많은 제품 라인에 유리하다.
- 약점: 플러그인 간 상호작용이 많아지면 커널을 거치는 간접 호출 비용과 설계 복잡도가 증가한다.
- 적합한 경우: 파생 차종/옵션별로 기능이 달라지는 제품, 진단/이벤트 처리기처럼 확장 포인트가 명확한
  서브시스템.

## 4. 이벤트 기반 (Event-Driven)

- 개념: 컴포넌트가 이벤트(신호/메시지)를 발행/구독하며 느슨하게 연결된다.
- 강점: 발행자와 구독자가 서로를 몰라도 되므로 결합도가 매우 낮고, 컴포넌트 추가/제거가 쉬워 변경
  유연성이 높다.
- 약점: 전체 흐름을 추적하기 어려워지고, 실시간성/결정론적 타이밍이 중요한 안전 관련 기능에는
  이벤트 지연·순서 보장 문제를 별도로 설계해야 한다(오류 격리·안전 동작 분석 필요).
- 적합한 경우: 차량 내 다수 센서/신호를 비동기로 처리하는 시스템, 상태 변화에 여러 구독자가 반응해야
  하는 시스템(단, 안전 관련이면 타이밍/순서 보장 메커니즘을 §9와 함께 반드시 설계).

## 5. 컴포넌트/서비스 기반 (Component-Based)

- 개념: 명시적인 제공(provided)/요구(required) 인터페이스를 가진 컴포넌트들을 조립해 시스템을
  구성한다. TPL-SWE2-002 drawio 템플릿의 표기(제공/요구 인터페이스)와 가장 직접적으로 대응한다.
- 강점: "컴포넌트는 인터페이스로만 통신한다"는 요건을 표기법 수준에서부터 강제하기 쉽고, 통합 순서
  정의(§6)와도 자연스럽게 연결된다.
- 약점: 컴포넌트 경계를 잘못 설정하면(너무 세분화/너무 뭉뚱그림) 응집도-결합도 균형이 무너질 수 있다.
- 적합한 경우: 범용적으로 적합 — 다른 스타일과 조합해서 쓰는 경우도 많다(예: 계층형 + 컴포넌트 기반).

## 6. 파이프-필터 (Pipe-Filter)

- 개념: 데이터가 여러 처리 단계(필터)를 순차적으로 통과하며 변환된다. 각 필터는 입력 파이프와 출력
  파이프(인터페이스)만 안다.
- 강점: 각 필터가 독립적이라 응집도가 높고, 필터 재배열/교체로 변경에 유연하게 대응할 수 있다.
- 약점: 상태를 공유해야 하는 처리나 양방향 상호작용에는 부적합하다.
- 적합한 경우: 센서 데이터 전처리/신호 처리 체인처럼 단방향 변환 파이프라인.

## 선택 시 고려 질문 (사용자에게 제시할 때 함께 안내)

- 어떤 부분이 앞으로 가장 자주 변경될 것으로 예상되는가? (그 지점을 인터페이스로 격리하는 스타일 선호)
- 안전 관련(ASIL) 요소가 있는가? 있다면 오류 격리/타이밍 결정성을 구조적으로 보장하기 쉬운 스타일인가?
- 팀이 이미 익숙한 스타일이 있는가? (학습 비용도 트레이드오프에 포함)
- 기존 상위 시스템 아키텍처나 플랫폼 제약(AUTOSAR 등)이 특정 스타일을 사실상 강제하는가?
