# 인터페이스 명세 가이드

SKILL.md §5(인터페이스 명세)에서 사용한다. "컴포넌트는 반드시 인터페이스로만 통신한다"를 문서와
다이어그램 양쪽에서 강제하기 위한 규칙이다.

## 1. 기본 규칙

- 컴포넌트 간 통신 경로 하나마다 인터페이스 하나 이상이 대응해야 한다. 다이어그램에 "인터페이스 없이
  컴포넌트 A → 컴포넌트 B" 화살표를 남기지 않는다.
- 인터페이스는 **제공자(provider)** 관점에서 이름을 짓는다(예: `IF-DIAG-001 진단데이터제공`). 사용자
  (consumer)는 여러 개일 수 있다.
- 외부(하드웨어/통신/사용자/외부서비스) 경계도 동일하게 인터페이스로 취급한다(템플릿 6.2 외부
  인터페이스).

## 2. 인터페이스 명세 항목 (템플릿 6장 대응)

| 속성 | 설명 |
|---|---|
| ID | 고유 식별자(예: `IF-XXX`), 재사용 금지 |
| 명칭 | 인터페이스가 제공하는 기능을 나타내는 이름 |
| 구분 | 내부(6.1) / 외부(6.2) |
| 제공자 | 이 인터페이스를 구현/제공하는 컴포넌트(`ARC-XXX`) |
| 사용자 | 이 인터페이스를 호출/구독하는 컴포넌트(`ARC-XXX`, 여러 개 가능) |
| 제공 기능/데이터 | 오퍼레이션, 이벤트, 데이터 구조 등 실제로 주고받는 내용 |
| 호출 조건 | 사전조건(호출 전 만족해야 할 상태), 사후조건(호출 후 보장되는 상태) |
| 시간 제약 | 응답 시간, 주기, 타임아웃 등 (해당하는 경우) |
| 오류 계약 | 오류 발생 시 반환값/예외/신호와 그 의미, 오류가 호출자에게 전파되는 방식 |
| 관련 요구사항 | 이 인터페이스가 만족시키는 SW 요구사항 ID (§8 요구사항 할당과 연결) |

## 3. 내부 인터페이스 (템플릿 6.1)

- 컴포넌트 간 API(함수/서비스 호출), 이벤트(발행/구독), 공유 데이터 저장소 접근을 모두 인터페이스로
  명시한다.
- 데이터 저장소를 여러 컴포넌트가 직접 읽고 쓰는 경우, "공유 데이터 접근"도 하나의 인터페이스로
  간주하고 동기화 규칙(락, 원자성, 갱신 주기)을 함께 정의한다 — 인터페이스 없는 암묵적 공유 상태를
  허용하지 않는다.

## 4. 외부 인터페이스 (템플릿 6.2)

- 하드웨어(센서/액추에이터), 차량 통신(예: CAN/이더넷 등 프로젝트에서 실제 사용하는 프로토콜), 사용자
  UI, 외부 서비스와의 경계를 각각 인터페이스로 정의한다.
- 외부 프로토콜의 정확한 신호/메시지 정의가 별도 문서(예: 통신 매트릭스)에 있다면 그 문서를 참조로
  링크하고, 이 문서에는 아키텍처 관점의 책임 분리(어느 컴포넌트가 변환/검증 책임을 갖는지)를 명확히
  한다.

## 5. 인터페이스 분리(ISP) 점검

- 한 인터페이스에 서로 다른 사용자가 필요로 하지 않는 오퍼레이션이 섞여 있지 않은지 확인한다.
- 사용자 그룹별로 필요한 기능이 다르면, 인터페이스를 역할별로 나눈다(예: `IF-DIAG-READ`와
  `IF-DIAG-WRITE`를 분리).

## 6. PlantUML 표현 예시

```
@startuml
component "컴포넌트 A" as A
component "컴포넌트 B" as B
interface "IF-XXX 기능제공" as IF
A -down- IF
IF -down- B : 사용
@enduml
```

- 위 초안을 검토한 뒤, 최종 산출물은 TPL-SWE2-002 drawio 템플릿의 제공/요구 인터페이스 표기로
  옮긴다(`references/template-source.md` 참고).
