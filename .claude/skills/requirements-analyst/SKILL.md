# 요구사항 분석가

이 스킬은 요구사항을 도출·분석·명세·검증하는 절차와 산출물 규칙을 제공한다. 목표는 다음 7가지 요건을
모두 만족하는 요구사항 산출물을 만드는 것이다.

1. 지정된 템플릿 준수 (템플릿이 없으면 §1의 잠정 구조 사용, 도착 시 즉시 전환)
2. ISO 26262 · A-SPICE 준수
3. 기능 요구사항 → UML/SysML 다이어그램(PlantUML)으로 표현 가능
4. 비기능 요구사항 → ISO 25010 기준 + 실행 가능한 검증방안
5. 명확성 (사람이 오해 없이 이해 가능)
6. 양방향 추적성 (모든 요구사항이 상/하위 산출물과 연결·유지됨)
7. 일관성 (용어/번호체계/내용이 서로 모순되지 않음)

## 0. 시작할 때 항상 할 일

1. `references/template-source.md`를 먼저 읽는다. 사용자가 지정 템플릿을 붙여넣었거나 경로를 남겨뒀으면
   **그 템플릿을 그대로 따른다** — 이 SKILL.md의 §1 잠정 구조는 무시한다.
2. 템플릿이 아직 없으면 §1의 잠정 구조를 사용하되, 산출물 상단에 "※ 회사 지정 템플릿 도착 전 잠정
   구조로 작성됨"이라고 명시한다.
3. `references/traceability-matrix.md`가 있으면 최신 상태를 읽어서 새 요구사항의 ID·추적 링크를
   기존 체계와 일관되게 이어간다 (없으면 새로 만든다).
4. 대상 프로젝트/제품, 요구사항 범위(신규 도출인지 기존 문서 분석인지), 안전 관련 여부(ISO 26262
   적용 대상인지)가 불명확하면 먼저 사용자에게 확인한다.

## 1. 요구사항 항목 구조 (템플릿 도착 전 잠정 구조)

ISO/IEC/IEEE 29148(요구사항 명세 국제표준)과 ISO 26262-8 6절(요구사항 명세 및 관리)의 공통 요건을
반영한 잠정 구조다. 각 요구사항은 최소 아래 속성을 가진다.

| 속성 | 설명 |
|---|---|
| ID | 고유 식별자 (§5 번호체계 참조). 이후 절대 재사용/변경하지 않는다 |
| 제목 | 한 줄 요약 |
| 설명 | §4 명확성 규칙(EARS)에 따라 서술한 요구사항 본문 |
| 유형 | 기능(FR) / 비기능(NFR) / 안전(Safety) |
| 출처 | 이 요구사항이 도출된 상위 요구사항, 이해관계자 요청, 위험분석 결과 등 |
| 근거/사유 | 왜 필요한지 (Rationale) |
| 우선순위 | 필수/권장/선택 등 |
| ASIL (해당 시) | ISO 26262 대상이면 QM/A/B/C/D와 연계된 Safety Goal ID 명시 |
| 검증방안 | 어떻게 검증할지 — NFR은 §3 규칙에 따라 실행 가능해야 함 |
| 추적 링크 | §6 참조 — 상위 근거, 하위 파생/설계/시험 항목 ID |
| 상태 | 초안/검토중/승인/구현중/검증완료 |

## 2. 기능 요구사항 — UML/SysML(PlantUML) 표현

자세한 다이어그램 문법과 예시는 `references/sysml-plantuml-guide.md` 참고. 요약:

- 기능 요구사항 하나마다 최소 하나의 유스케이스(액터-목표)로 연결한다. 상호작용이 복잡하면 시퀀스
  다이어그램이나 상태 다이어그램을 추가한다.
- SysML 요구사항 다이어그램은 PlantUML에서 `<<requirement>>`, `<<block>>` 스테레오타입과
  `<<deriveReqt>>`, `<<satisfy>>`, `<<verify>>`, `<<refine>>`, `<<trace>>` 관계로 표현한다(SysML이
  UML 프로파일 확장이라는 원리를 그대로 이용). 이 다이어그램은 §6 추적성 매트릭스와 반드시 일치해야
  한다 — 다이어그램에만 있고 매트릭스에 없는 관계, 혹은 그 반대는 일관성 위반으로 처리한다.
- PlantUML 소스는 `.puml` 파일로 저장하고, 요구사항 문서에서 파일 경로로 참조한다 (렌더링은 별도
  PlantUML 도구/플러그인이 필요하다는 점을 사용자에게 알려준다).

## 3. 비기능 요구사항 — ISO 25010 + 실행 가능한 검증방안

`references/iso25010-nfr-checklist.md`에 8대 품질특성(기능적합성, 성능효율성, 호환성, 사용성,
신뢰성, 보안성, 유지보수성, 이식성)과 하위특성, 작성 예시가 있다. 규칙:

- 모든 비기능 요구사항은 8대 품질특성 중 하나 이상에 명시적으로 매핑한다.
- 검증방안은 **측정 가능한 기준값 + 실제로 수행 가능한 절차/도구**를 포함해야 한다. "정성적으로 확인",
  "육안으로 검토" 같은 모호하거나, 존재하지 않는 도구/불가능한 환경을 전제로 한 검증방안은 금지한다.
  - 나쁜 예: "시스템은 충분히 빨라야 한다" / 검증: "사용자가 만족하는지 확인"
  - 좋은 예: "정상 부하(동시 사용자 100명) 조건에서 API 응답시간의 P95가 200ms 이하여야 한다" /
    검증: "JMeter로 100 VU, 5분 지속 부하 테스트를 수행하고 P95 응답시간을 측정한다"
- 검증방안을 제안하기 전에 실제로 그 방법이 현재 프로젝트 환경에서 수행 가능한지(도구 존재, 접근 권한,
  측정 가능성) 확인한다. 확인할 수 없으면 "실행 가능 여부 확인 필요"로 표시하고 확정하지 않는다.

## 4. 명확성 — EARS 문형 사용

자세한 패턴은 `references/ears-writing-patterns.md` 참고. 핵심 원칙:

- 요구사항 하나에는 하나의 검증 가능한 주장만 담는다 (원자성). "그리고", "또는"으로 여러 요구를
  묶지 않는다.
- 애매한 형용사(빠르게, 적절히, 충분히, 사용자 친화적으로 등)를 단독으로 쓰지 않는다 — 반드시
  측정 가능한 기준으로 구체화한다.
- EARS(Easy Approach to Requirements Syntax) 문형(유비쿼터스/이벤트기반/상태기반/원치 않는 동작/
  선택기능/복합)을 사용해 트리거·조건·주체·응답을 명확히 구분한다.

## 5. ID/번호체계 (일관성의 기반)

- 이해관계자 요구사항: `StR-XXX`
- 시스템 요구사항: `SR-XXX`
- 소프트웨어 요구사항: `SWR-XXX`
- 비기능 요구사항: 유형 접두사에 `-NFR` 접미 또는 별도 `NFR-XXX` (프로젝트 내에서 하나로 통일)
- 안전 요구사항: 위 접두사 + Safety Goal 연계 (`SG-XXX` → `SR-XXX` 등)
- 번호는 순증가만 하며 삭제된 ID는 재사용하지 않는다(추적 이력 보존).
- 이미 다른 번호체계가 프로젝트에 있으면(예: 템플릿에 지정됨) 그것을 따르고 이 절은 무시한다.

## 6. 양방향 추적성

`references/traceability-matrix-template.md` 형식을 사용해 `references/traceability-matrix.md`
(또는 사용자가 지정한 위치)를 프로젝트의 단일 진실 공급원(single source of truth)으로 유지한다.

- 모든 요구사항은 **위로**(왜 이게 필요한가 — 상위 요구사항/이해관계자 요청/위험분석) 그리고
  **아래로**(무엇으로 구현/검증되는가 — 설계 요소, 코드 모듈, 테스트 케이스) 최소 1개 이상 연결되어야
  한다. 연결이 없는 요구사항(고아 요구사항)이나, 어떤 요구사항으로도 연결되지 않는 설계/테스트
  항목(근거 없는 산출물)은 결함으로 보고한다.
- 요구사항을 새로 만들거나 수정할 때마다, 같은 작업 안에서 추적성 매트릭스도 함께 갱신한다 — "나중에
  갱신"은 허용하지 않는다.
- UML/SysML 요구사항 다이어그램(§2)의 관계와 매트릭스 내용이 항상 일치하도록 유지한다.

## 7. 일관성 검토

산출물을 마무리하기 전에 다음을 점검한다.

- 동일 용어가 문서 전체에서 같은 의미로 쓰였는가 (용어집이 있으면 그것을 기준으로, 없으면 이번에
  등장한 용어를 일관되게 사용)
- 서로 모순되는 요구사항이 없는가 (예: 한 요구사항은 기능을 금지하고 다른 요구사항은 요구하는 경우)
- 번호체계가 §5 규칙(또는 템플릿 규칙)과 어긋나지 않는가
- 중복 요구사항(다른 ID로 같은 내용을 반복)이 없는가

## 8. ISO 26262 · A-SPICE 관련 유의사항

`references/iso26262-aspice-checklist.md`에 요구사항 속성/추적성 관련 체크포인트가 있다. 단, 두
표준의 정확한 조항 번호·원문 인용이 필요한 경우, 이 스킬의 요약만으로 단정하지 말고 프로젝트에 첨부된
공식 표준 문서(있다면)를 함께 확인한다 — 컴플라이언스 문서이므로 부정확한 원문 인용을 피해야 한다.
