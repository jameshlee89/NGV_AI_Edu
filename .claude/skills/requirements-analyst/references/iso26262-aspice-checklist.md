# ISO 26262 · A-SPICE 요구사항 관련 체크포인트 (요약 — 원문 대조 필요)

> ⚠️ 아래는 요구사항 문서 작성 시 반영해야 할 항목을 정리한 **요약**이다. 실제 감사/인증 대응 문서에
> 조항 번호나 원문을 인용해야 한다면, 이 요약만으로 단정하지 말고 프로젝트에 첨부된 공식 표준 문서로
> 정확한 조항 번호와 문구를 확인한다.

## ISO 26262 관점

- 요구사항은 **고유하게 식별**되어야 하고(ID 재사용 금지), 각 요구사항은 **검증 가능**해야 한다
  (통과/실패를 판정할 기준이 있어야 함) — 이는 이 스킬의 §4(EARS), §3(실행 가능한 검증방안)과 직결된다.
- 요구사항은 **원자적**이어야 한다(하나의 요구사항 = 하나의 검증 가능한 주장). 여러 요구를 한 문장에
  묶지 않는다.
- 안전 관련 요구사항은 **ASIL 등급**과 그 근거가 된 **Safety Goal**까지 추적 가능해야 한다. 요구사항
  구조(§1 표)의 "ASIL" 속성과 §6 추적성 매트릭스의 상위 ID 컬럼으로 이를 충족한다.
- 요구사항 명세와 관리 과정 자체에서 **양방향 추적성**이 명시적으로 요구된다 — 상위 요구사항으로의
  추적(왜 필요한가)과 하위 산출물로의 추적(어떻게 구현/검증되는가) 모두. 이 스킬의 §6이 이를 위한
  구체적 방법(RTM + 다이어그램 동기화)이다.
- 요구사항은 명확·정확·일관·실현 가능해야 하며, 검증 담당자가 해당 요구사항만으로 시험 케이스를
  도출할 수 있을 정도로 구체적이어야 한다.

## A-SPICE 관점 (요구사항 관련 프로세스)

- **SYS.1 요구사항 도출**, **SYS.2 시스템 요구사항 분석**, **SWE.1 소프트웨어 요구사항 분석** 등
  요구사항 관련 프로세스는 공통적으로 다음을 기대한다.
  - 요구사항의 구조화(속성 정의, 우선순위, 상태 등) — §1 표
  - 이해관계자/상위 요구사항과의 **일관성 확보 및 양방향 추적성 유지** — §6, §7
  - 요구사항에 대한 검토(리뷰)와 이해관계자 합의
  - 요구사항 변경의 영향 분석(추적성 매트릭스를 통해 영향 범위 파악)
- 정확한 Base Practice 번호/문구가 필요하면 `.claude/skills/aspice-auditor/references/aspice-source.md`
  또는 공식 A-SPICE 4.1 문서를 확인한다(이미 이 저장소에 A-SPICE 감사 스킬이 있으므로 중복 작성하지
  않고 그쪽을 참조한다).

## 이 스킬이 두 표준을 만족시키는 방식 요약

| 표준 요건 | 이 스킬의 대응 |
|---|---|
| 고유 식별/추적성 | §5 ID체계 + §6 RTM |
| 검증 가능성 | §3 실행 가능한 검증방안 규칙, §4 EARS |
| 원자성/명확성 | §4 EARS 체크리스트 |
| 일관성 | §7 일관성 검토 |
| ASIL/Safety Goal 연계 | §1 요구사항 속성 표의 ASIL 필드 |
