# 양방향 추적성 매트릭스 (Requirements Traceability Matrix, RTM)

이 파일 형식을 그대로 복사해서 `references/traceability-matrix.md`(또는 사용자가 지정한 위치)에
프로젝트의 실제 매트릭스로 유지한다. 요구사항을 새로 만들거나 수정할 때마다 같은 작업에서 함께
갱신한다 — 나중으로 미루지 않는다.

## 매트릭스

| 하위 ID | 유형 | 상위(근거) ID | 설계 요소 | 테스트 케이스 ID | 검증 상태 | 비고 |
|---|---|---|---|---|---|---|
| SR-010 | 기능 | StR-001 | (해당 설계 문서/모듈명) | TC-010 | 미검증 | |
| SWR-020 | 기능 | SR-010 | (해당 모듈명) | TC-020 | 미검증 | |
| NFR-030 | 비기능(성능효율성) | StR-002 | (해당 컴포넌트) | TC-030 | 미검증 | |

## 유지 규칙

1. **고아 요구사항 금지**: "상위(근거) ID"가 없는 요구사항(왜 필요한지 설명 불가)이 있으면 안 된다.
   이해관계자 요구사항(StR)처럼 최상위인 경우는 예외로 "이해관계자 요청/시장 조사" 등 출처를 적는다.
2. **근거 없는 산출물 금지**: 어떤 요구사항 ID와도 연결되지 않는 설계 요소나 테스트 케이스가 있으면
   결함으로 보고한다 (범위를 벗어난 과잉 구현이거나, 매트릭스 갱신 누락).
3. **양방향 확인**: 요구사항 관점(위/아래로 무엇이 연결됐는지)과 산출물 관점(이 설계/테스트가 어떤
   요구사항 때문에 존재하는지) 양쪽에서 조회 가능해야 한다 — 표 하나로 양방향이 되지 않으면 역방향
   조회용 보조 표나 필터링 방법을 함께 제공한다.
4. **다이어그램과 동기화**: `references/sysml-plantuml-guide.md`의 SysML 요구사항 다이어그램에 그린
   `<<deriveReqt>>`/`<<satisfy>>`/`<<verify>>` 관계는 이 표의 내용과 항상 일치해야 한다.
5. **삭제 대신 상태 변경**: 요구사항이 더 이상 유효하지 않아도 행을 삭제하지 않고 "폐기"로 상태를
   표시해 이력을 보존한다 (ID 재사용 금지 원칙과 동일한 이유).
