# 상세설계자

이 스킬은 아키텍처 설계 결과를 구현 가능한 수준(모듈, 함수, 자료형, 알고리즘)으로 구체화하고, 회사
지정 양식으로 상세설계서를 작성하는 절차와 규칙을 제공한다. 목표는 다음 요건을 모두 만족하는 상세설계
산출물을 만드는 것이다.

1. 지정된 템플릿(TPL-SWE3-001, TPL-SWE3-002) 준수
2. A-SPICE(SWE.3) · ISO 26262 Part 6 단위 설계 원칙 준수
3. 상위 아키텍처 설계서(SWE.2 산출물)와의 정합성 — 상세설계는 아키텍처를 재정의하지 않고 구체화한다
4. 모듈/함수 수준에서도 높은 응집도 · 낮은 결합도 유지
5. 모든 핵심 함수에 명확한 계약(입력/출력/사전조건/사후조건/부작용/예외/시간 제약) 정의
6. 알고리즘·정책 의사결정표의 완전성과 일관성 확보
7. 오류·예외에 대한 방어적 동작 정의
8. 요구사항·아키텍처·구현 단위·단위시험 간 양방향 추적성 확보

## 0. 시작할 때 항상 할 일

1. `references/template-source.md`를 읽는다. 회사 지정 상세설계서 템플릿(TPL-SWE3-001 docx,
   TPL-SWE3-002 drawio)이 이미 저장소에 있으므로, 이 SKILL.md의 장 구성을 그대로 목차로 사용해 작성한다.
2. **근거 아키텍처 설계서를 먼저 확인한다.** `architecture-design` 스킬로 작성된 SWE.2 산출물(또는
   그에 준하는 아키텍처 문서)을 찾아 읽고, 이번 상세설계가 다루는 아키텍처 요소(`ARC-XXX`)와 인터페이스
   (`IF-XXX`) 범위를 확정한다. 찾을 수 없으면 사용자에게 위치를 확인한다 — 아키텍처 근거 없이 상세설계를
   임의로 시작하지 않는다.
3. 관련 SW 요구사항 문서, 기존 코딩 표준/정적분석 설정(있다면)이 있으면 함께 읽는다.
4. 대상 범위, 구현 언어/플랫폼, 안전 관련 여부(ASIL, 관련 Safety Requirement)가 불명확하면 먼저
   사용자에게 확인한다.

## 2. 아키텍처 정합성 확인 (필수 선행 단계)

상세설계를 시작하기 전에 다음을 확인한다.

- [ ] 이번에 다룰 아키텍처 요소(`ARC-XXX`)와 그 책임이 아키텍처 설계서와 정확히 일치하는가?
- [ ] 이 요소가 제공/사용하는 인터페이스(`IF-XXX`)가 아키텍처 설계서에 정의된 것과 동일한가? 상세설계
      단계에서 새로운 공개 인터페이스를 추가해야 한다면, 먼저 아키텍처 설계서 갱신이 필요함을 사용자에게
      알린다(상세설계에서 인터페이스 계약을 몰래 바꾸지 않는다).
- [ ] 아키텍처 설계서의 통합 순서(있다면)와 이번 상세설계 대상 모듈의 구현 우선순위가 상충하지 않는가?

## 3. 모듈 분해 · 상세 호출관계 · 공통 자료형

- 아키텍처 요소를 구현 단위(모듈/클래스/함수 그룹)로 분해하고, 각 단위에 ID(예: `UNIT-XXX`), 명칭,
  책임, 소스 위치(예정 경로)를 부여한다.
- 단위 하나는 하나의 명확한 책임만 갖도록 한다(응집도) — `references/unit-design-principles-
  checklist.md`의 응집도/결합도 체크리스트로 점검한다.
- 함수/클래스 간 호출 순서와 의존 방향을 정의하고, 아키텍처 설계서의 정적 의존성(순환 의존 금지)과
  모순되지 않는지 확인한다.
- 공통 데이터 구조, 열거형, 단위(unit), 유효범위, 불변조건, 직렬화 규칙을 정의해 여러 단위가 같은
  자료형을 일관되게 사용하도록 한다.
- 로직/호출관계는 PlantUML(`.puml`) 클래스/시퀀스 다이어그램으로 초안을 작성해 빠르게 검토한 뒤,
  최종 산출물은 §9에 따라 TPL-SWE3-002 drawio 구조로 정리한다.

## 4. 핵심 함수 계약 · Web/API 상세

`references/function-contract-guide.md`에 상세 규칙과 표 형식이 있다. 핵심 규칙:

- 아키텍처 인터페이스(`IF-XXX`)를 구현하는 모든 공개 함수와, 복잡도가 높거나 오류 가능성이 있는 내부
  함수는 계약을 명세한다: 입력, 출력, 사전조건, 사후조건, 부작용(side effect), 예외/오류 반환, 시간
  제약(해당 시).
- Web/API 엔드포인트가 있으면 엔드포인트별로 요청/응답 구조, 입력 검증 규칙, 오류 코드, 세션/인증
  경계, 보안 경계를 함수 계약과 동일한 엄밀도로 정의한다(템플릿 9장).
- 계약 없이 알고리즘만 서술하지 않는다 — 계약이 곧 이 함수가 지켜야 할 검증 가능한 약속이다.

## 5. 핵심 알고리즘 · 정책 의사결정표

`references/algorithm-decision-guide.md`에 상세 규칙이 있다. 핵심 규칙:

- 핵심 알고리즘은 의사코드 또는 흐름도로 처리 순서, 판단 조건, 경계값, 계산 근거를 표현한다.
- 여러 입력 조건의 조합으로 동작이 달라지는 정책은 의사결정표로 정의하고, 모든 조건 조합이
  다뤄지는지(완전성)와 서로 다른 행이 같은 조건에서 다른 결과를 내지 않는지(일관성)를 점검한다.
- 실행 가능 여부가 불확실한 알고리즘(예: 존재를 확인하지 못한 라이브러리/하드웨어 기능에 의존)은
  확정하지 말고 "확인 필요"로 표시한다.

## 6. 상태전이 상세 · 오류와 방어 동작

- 상태를 갖는 단위는 상태 저장 위치, 전이 함수, 이벤트, 가드, 타이머, 초기화 동작을 정의한다(템플릿
  8장). 아키텍처 설계서의 상태 전이(있다면)와 상태 이름·전이 조건이 일치해야 한다.
- `references/error-handling-defensive-guide.md`에 따라 유효하지 않은 입력, 예외, 자원 실패(메모리,
  통신, 파일 등)에 대한 검출·처리·기록·복구 동작을 정의한다(템플릿 10장). 안전 관련(ASIL) 단위는
  아키텍처 설계서의 오류 격리/안전 상태 정의와 일치하는 구체적 구현 방법을 제시한다.

## 7. 코딩 및 검증 규칙 · 단위 설계 원칙

`references/unit-design-principles-checklist.md`에 상세 체크리스트가 있다. 핵심 규칙:

- 프로젝트에 지정된 코딩 표준(예: MISRA류 규칙, 사내 스타일 가이드)이 있으면 그것을 우선 인용하고,
  없으면 이 스킬의 체크리스트를 잠정 기준으로 사용하되 "사내 코딩표준 확인 필요"로 표시한다.
- ISO 26262 Part 6의 단위 설계·구현 원칙(복잡도 제한, 방어적 프로그래밍, 포인터/재귀/인터럽트 사용
  제한 등)을 반영한다. 정확한 절 번호·원문은 `references/iso26262-aspice-detailed-design-
  checklist.md`의 안내에 따라 공식 표준 문서로 확인한다.
- 정적분석, 단위검증(단위시험), 커버리지, 코드 리뷰 기준을 명시한다. 실제 단위시험 산출물은 별도
  템플릿(`WP_Templates/Engineering/SoftwareUnitVerification/TPL-SWE4-*`)을 따르므로, 이 스킬은 그
  산출물이 참조할 수 있도록 단위 ID·함수 계약을 명확히 남기는 데 집중한다.

## 8. 요구사항 할당 및 추적성

- SW 요구사항(`SWR-XXX`)과 아키텍처 요소(`ARC-XXX`)를 구현 단위(`UNIT-XXX`)·함수·단위시험 항목까지
  연결한다(템플릿 12장).
- 할당 누락(어떤 요구사항도 커버하지 못하는 단위가 없는지, 어떤 단위로도 할당되지 않은 요구사항이
  없는지)과 중복 할당을 점검한다.
- 프로젝트에 추적성 매트릭스(`requirements-analyst` 스킬의 `references/traceability-matrix.md`,
  `architecture-design` 스킬 산출물 등)가 있으면, 상세설계 ID를 같은 작업 안에서 함께 갱신한다(템플릿
  14장). "나중에 갱신"은 허용하지 않는다.

## 9. 다이어그램 작성 규칙

- 설계 중 빠른 검토용으로 PlantUML(`.puml`) 클래스/시퀀스/상태 다이어그램을 먼저 작성한다.
- 공식 베이스라인 산출물은 회사 지정 `TPL-SWE3-002_상세설계 UML 및 호출관계 템플릿.drawio`를 복사해
  사용하고, 다음을 반드시 포함한다: 구현 단위와 책임, 함수/클래스 호출 관계, 입력/출력 자료형, 설계 및
  시험 추적 ID. 안내 도형(플레이스홀더)은 실제 요소로 교체하고 남겨두지 않는다.
- PlantUML 초안과 drawio 최종본, 그리고 상위 아키텍처 다이어그램(TPL-SWE2-002)의 요소·관계가 서로
  모순되지 않아야 한다.

## 10. 구현 경계 및 SBOM/라이선스 관련 유의사항

- 템플릿 13장(구현 경계)에서 생성 코드, 외부 라이브러리, 플랫폼 종속부, 구현하지 않는 범위를 명시한다.
- 외부 라이브러리(특히 오픈소스)를 사용하면, 실제 구현/통합 단계에서 `WP_Templates/Engineering/
  SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_Python 의존성 SBOM FOSS 라이선스 목록
  템플릿.xlsx`(SWE.3/SUP.8 적용)에 패키지·버전·의존성 유형·SPDX 라이선스·근거 위치를 기록해야 함을
  사용자에게 알린다. 이 스킬 자체는 SBOM을 채우는 스킬이 아니므로, 상세설계서에는 "외부 라이브러리
  사용 예정 → SBOM 기록 필요"만 명시하고 실제 SBOM 작성은 별도 작업으로 안내한다.

## 11. 산출물 저장 및 파일명 규칙

- 상세설계서(TPL-SWE3-001)와 UML(TPL-SWE3-002)을 실제로 작성할 때는 `WP_Templates/Engineering/
  SoftwareDetailedDesignAndUnitConstruction/`의 원본 템플릿을 복사한 뒤, `WP_Templates/Engineering/
  README.md`의 규칙대로 파일명을 `<산출물 ID>_<산출물명>.<확장자>` 형식으로 바꾸고 프로젝트/베이스라인
  정보를 채운다. 저장 위치를 사용자가 지정하지 않았다면 어디에 저장할지 먼저 확인한다.
- 템플릿 ID·적용 산출물·실제 파일 위치는 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`에
  기록되어 있으므로, 새 산출물을 등록해야 하는지 사용자에게 확인한다.

## 12. 최종 자체 검토 체크리스트

산출물을 마무리하기 전에 다음을 점검한다.

- [ ] 이번 상세설계가 다루는 아키텍처 요소/인터페이스가 아키텍처 설계서와 정확히 일치하는가 (§2)
- [ ] 각 구현 단위가 단일하고 명확한 책임을 갖는가 (응집도)
- [ ] 단위 간 호출/의존이 아키텍처의 정적 의존성과 모순되지 않고 순환 의존이 없는가 (결합도)
- [ ] 모든 공개 함수/API에 사전조건·사후조건·예외 계약이 정의되어 있는가 (§4)
- [ ] 알고리즘/정책 의사결정표가 완전하고 일관적인가 (§5)
- [ ] 오류·예외에 대한 방어 동작이 정의되어 있는가 (§6)
- [ ] 단위 설계 원칙(복잡도 제한, 방어적 프로그래밍 등) 위반이 없는가 (§7)
- [ ] 모든 SW 요구사항이 구현 단위에 할당되었는가, 고아 요구사항/근거 없는 단위가 없는가 (§8)
- [ ] PlantUML 초안과 TPL-SWE3-002 drawio 최종본, 상위 아키텍처 다이어그램이 서로 일치하는가 (§9)
- [ ] 외부 라이브러리 사용 시 SBOM 기록 필요성을 안내했는가 (§10)
- [ ] ISO 26262/A-SPICE 조항을 원문 확인 없이 단정적으로 인용하지 않았는가
