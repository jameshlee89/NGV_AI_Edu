# 오류 처리 · 방어적 프로그래밍 가이드

SKILL.md §6(오류와 방어 동작)에서 사용한다. 템플릿 10장(오류와 방어 동작)에 대응하며, 아키텍처
설계서의 오류 격리/안전 동작(SWE.2 산출물 §7~9장)을 구현 가능한 수준으로 구체화한다.

## 1. 다뤄야 할 오류 유형

- **유효하지 않은 입력**: 함수 계약(§4)의 사전조건을 위반하는 입력. 방어적으로 검사하고 명확한
  오류로 반환할지, 상위에서 이미 보장된다고 간주할지(그 근거 포함)를 명시한다.
- **예외/실패**: 연산 실패(오버플로, 0으로 나누기 등), 외부 자원 실패(메모리 부족, 통신 끊김, 파일
  접근 실패 등).
- **자원 실패**: 하드웨어/드라이버 접근 실패, 타임아웃.

## 2. 각 오류 유형에 대해 정의할 항목

| 항목 | 설명 |
|---|---|
| 검출 (Detection) | 오류를 어디서, 어떤 검사로 감지하는가 |
| 처리 (Handling) | 감지 후 즉시 어떤 조치를 취하는가(재시도, 기본값 사용, 안전 상태 전환 등) |
| 전파 차단 | 이 오류가 호출자/다른 컴포넌트로 어떻게(어떤 형태로) 전달되는가, 전파를 어디서 멈추는가 |
| 기록 (Logging) | 진단을 위해 어떤 정보를 남기는가 |
| 복구 (Recovery) | 정상 동작으로 복귀하는 조건과 절차, 복귀 불가 시의 대응 |

## 3. 방어적 프로그래밍 원칙

- 신뢰할 수 없는 경계(외부 입력, 외부 시스템 응답, 사용자 입력)를 넘어오는 모든 데이터는 사용 전에
  검증한다.
- 실패를 조용히 무시하지 않는다 — 모든 오류 경로는 §2의 항목이 채워져야 한다.
- 안전 관련(ASIL) 단위는 아키텍처 설계서에서 정의한 안전 상태(safe state)로 실제로 전이시키는 구체적
  코드/절차를 제시한다. 안전 상태 정의 자체를 이 단계에서 새로 만들지 않고, 아키텍처 설계서를
  따른다(불일치 시 아키텍처 설계서 갱신을 사용자에게 제안).
- "예외적으로 발생하지 않는다고 가정한다" 같은 근거 없는 전제로 오류 처리를 생략하지 않는다 — 실제로
  발생할 수 없음을 설계/요구사항 근거로 보일 수 있을 때만 생략하고, 그 근거를 문서에 남긴다.

## 4. §1 단위 설계 원칙과의 연결

포인터/동적 메모리/재귀 등 ISO 26262 단위 설계 원칙(`references/unit-design-principles-
checklist.md` §4)을 제한적으로 사용하는 경우, 그 사용이 실패했을 때의 방어 동작도 이 절의 규칙에
따라 함께 정의한다.
