# 함수 계약 (Design by Contract) 작성 가이드

SKILL.md §4(핵심 함수 계약)에서 사용한다. 템플릿 5장(핵심 함수 계약), 9장(Web 및 API 상세)에 대응한다.

## 1. 계약을 작성해야 하는 함수

- 아키텍처 설계서의 인터페이스(`IF-XXX`)를 구현하는 모든 공개 함수/오퍼레이션
- 복잡한 로직을 담고 있거나 오류 가능성이 있는 내부 함수(§6 핵심 알고리즘과 연결되는 함수)
- Web/API 엔드포인트로 노출되는 모든 오퍼레이션

## 2. 계약 명세 항목

| 속성 | 설명 |
|---|---|
| 함수/오퍼레이션 ID | 고유 식별자(예: `FN-XXX`), 관련 인터페이스 ID(`IF-XXX`)와 연결 |
| 시그니처 | 함수명, 매개변수 타입, 반환 타입 |
| 입력 | 각 매개변수의 의미, 유효 범위 |
| 출력 | 반환값의 의미, 유효 범위 |
| 사전조건 (Precondition) | 호출 전 호출자가 보장해야 하는 상태/입력 조건 |
| 사후조건 (Postcondition) | 정상 종료 시 함수가 보장하는 상태/결과 |
| 불변조건 (Invariant) | 함수 실행 전후로 유지되어야 하는 상태(해당 시) |
| 부작용 (Side Effect) | 전역 상태 변경, 외부 자원(파일/통신/하드웨어) 접근 등 |
| 예외/오류 | 실패 시 반환값·예외·오류 코드와 그 의미, 호출자가 취해야 할 조치 |
| 시간 제약 | 최대 실행 시간, 주기, 타임아웃(해당 시) |
| 관련 요구사항 | 이 함수가 만족시키는 SW 요구사항/아키텍처 인터페이스 ID |

## 3. 작성 원칙

- **사전조건은 호출자 책임, 사후조건은 함수 책임**이다 — 사전조건을 만족하지 않고 호출했을 때의
  동작(예: 방어적으로 오류 반환할지, 정의되지 않은 동작으로 간주할지)을 명시적으로 정한다. 안전
  관련(ASIL) 함수는 반드시 방어적으로 처리한다(§6 오류와 방어 동작 참고).
- 사후조건은 실제로 검증 가능한 형태로 쓴다("적절히 처리한다" 금지, "성공 시 반환값은 0 이상이고
  내부 버퍼 상태는 X이다"처럼 구체화).
- 인터페이스를 구현하는 함수의 계약은 아키텍처 설계서의 해당 인터페이스 명세(호출 조건, 오류 계약)와
  모순되지 않아야 한다 — 다르면 어느 쪽이 맞는지 확인 후 일치시킨다.
- 계약을 확정할 수 없는 부분(예: 외부 라이브러리의 실제 동작을 확인하지 못한 경우)은 "확인 필요"로
  표시하고 단정하지 않는다.

## 4. Web/API 오퍼레이션 추가 항목 (템플릿 9장)

| 속성 | 설명 |
|---|---|
| 엔드포인트 | 경로, HTTP 메서드 또는 프로토콜 오퍼레이션 |
| 요청 구조 | 필드, 타입, 필수 여부, 유효성 검증 규칙 |
| 응답 구조 | 성공/실패 각각의 필드, 타입 |
| 오류 코드 | 오류 상황별 코드/메시지와 의미 |
| 인증/세션 | 인증 방식, 세션 유지 방식, 권한 경계 |
| 보안 경계 | 입력 sanitization, 인가 검사 위치, 민감정보 처리 방식 |

## 5. PlantUML 표현 예시 (시퀀스로 사전/사후조건 맥락 표현)

```
@startuml
participant "호출자" as Caller
participant "FN-XXX" as Fn
Caller -> Fn : 호출 (사전조건 X 충족)
Fn -> Fn : 처리
Fn --> Caller : 반환 (사후조건 Y 보장)
@enduml
```
