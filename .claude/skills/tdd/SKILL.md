# TDD (테스트 주도 개발)

> 출처: 이 스킬은 [obra/superpowers](https://github.com/obra/superpowers)
> `skills/test-driven-development`(MIT License)를 한국어로 번역·각색하고, 이 프로젝트의 CLAUDE.md
> 구현 지침(품질 지표, Python 3.14/unittest, 상세설계 연계)을 결합해 구성했다.

## 개요

**테스트를 먼저 작성한다. 실패하는 것을 확인한다. 통과시키는 최소한의 코드를 작성한다.**

**핵심 원칙**: 테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수
없다.

**규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것이다.**

## 언제 사용하는가

**항상 적용**:
- 새 기능 구현
- 버그 수정
- 리팩터링
- 동작 변경

**예외(사용자에게 명시적으로 확인 필요)**:
- 일회성 프로토타입
- 자동 생성 코드
- 설정 파일

"이번만 TDD를 건너뛰자"라는 생각이 든다면 멈춘다 — 그것은 합리화다.

## 철칙 (The Iron Law)

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다
```

테스트보다 코드를 먼저 작성했다면? **삭제하고 처음부터 다시 시작한다.**

**예외 없음**:
- "참고용"으로 남겨두지 않는다
- 테스트를 작성하면서 그 코드를 "손봐서" 재사용하지 않는다
- 쳐다보지 않는다
- 삭제는 삭제다

테스트로부터 새로 구현한다. 예외 없음.

## 적용 범위와 인접 스킬과의 경계

이 스킬은 **함수/모듈 단위의 화이트박스 구현과 테스트**(CLAUDE.md 구현 지침 성격)만 다룬다. 아래
항목은 이 스킬이 담당하지 않는다.

| 대상이 아닌 것 | 담당 스킬 |
|---|---|
| 아키텍처 설계서의 인터페이스·통합 순서에 근거한 통합시험, 함수/Call 커버리지 | `integration-testing` |
| SW 요구사항 명세서 기반 블랙박스 기능/비기능 시스템 시험 | `sw-system-test` |
| 상세설계 자체의 작성(함수 계약, 알고리즘, 상태전이 설계) | `detailed-design` |

이 스킬의 테스트는 **상세설계서의 함수 계약**을 유일한 근거로 삼는다 — 여러 컴포넌트를 아우르는
통합 시나리오나 요구사항 전체를 검증하는 시스템 시험 케이스는 여기서 만들지 않는다.

## 0. 시작할 때 항상 할 일

1. 구현 근거가 되는 상세설계서(SWE.3, `detailed-design` 스킬 산출물)를 찾아 읽는다. 이번에 구현할
   단위(`UNIT-XXX`)의 함수 계약(입력/출력/사전조건/사후조건/예외/경계값)을 확인한다. 찾을 수 없으면
   사용자에게 위치를 확인한다.
2. 프로젝트에 지정된 코딩 표준(예: `.pylintrc`, `pyproject.toml`의 lint 설정, 사내 스타일 가이드)이
   있는지 `Glob`으로 확인한다. 있으면 그 표준을 이 스킬의 잠정 기준보다 우선 적용한다.
3. `Bash`로 `python --version`(또는 `python3 --version`)을 실행해 Python 3.14 계열 인터프리터가
   실제로 사용 가능한지 확인한다. 다르면 사용자에게 알리고, 어떤 버전으로 진행할지 확인한다.
4. `references/quality-metrics-tools.md`가 안내하는 품질 측정 도구(radon, flake8/mccabe, pylint,
   cloc 등)가 설치되어 있는지 확인한다. 없으면 설치 여부를 사용자에게 먼저 확인한다 — 도구 없이
   "지표를 만족했다"고 단정하지 않는다.

## 1. Red-Green-Refactor 사이클

```
[RED] 실패하는 테스트 하나를 작성한다
   │
   ▼
[Verify RED] 올바른 이유로 실패하는지 확인한다 (필수, 절대 생략 금지)
   │  실패 이유가 틀림 ──▶ 테스트를 고치고 다시 확인
   │  올바르게 실패함
   ▼
[GREEN] 테스트를 통과시키는 가장 단순한 코드를 작성한다
   │
   ▼
[Verify GREEN] 전체 테스트가 통과하는지 확인한다 (필수, 절대 생략 금지)
   │  실패함 ──▶ 테스트가 아니라 코드를 고친다
   │  전부 통과
   ▼
[REFACTOR] GREEN을 유지하면서 정리한다 (§6 품질 지표 반영)
   │
   ▼
다음 실패 테스트로 반복
```

### RED — 실패하는 테스트 작성

기대하는 동작 하나를 보여주는 최소한의 테스트를 작성한다.

**요구사항**:
- 하나의 동작만 검증한다
- 이름만으로 무엇을 검증하는지 알 수 있다
- 실제 코드를 사용한다(불가피한 경우가 아니면 모의 객체를 쓰지 않는다)
- §7(테스트 문서화 규칙)에 따라 Doxygen 형식 목적 설명·기법·긍정/부정 케이스를 함께 기록한다

### Verify RED — 실패를 직접 확인 (필수, 절대 생략 금지)

```
python -m unittest <테스트 경로>
```

다음을 확인한다:
- 테스트가 (에러가 아니라) **실패**하는가
- 실패 메시지가 예상한 내용인가
- 기능이 없어서 실패하는 것이지, 오타 때문에 실패하는 것이 아닌가

**테스트가 통과한다면?** 이미 존재하는 동작을 테스트하고 있는 것이다. 테스트를 고친다.

**테스트가 에러를 낸다면?** 에러를 고치고, 올바르게 실패할 때까지 다시 실행한다.

### GREEN — 최소 구현

테스트를 통과시키는 가장 단순한 코드를 작성한다. 테스트가 요구하지 않는 기능을 미리 만들거나, 다른
코드를 함께 "개선"하지 않는다(YAGNI).

### Verify GREEN — 통과를 직접 확인 (필수)

```
python -m unittest discover
```

다음을 확인한다:
- 이번 테스트가 통과하는가
- 기존의 다른 테스트도 여전히 통과하는가
- 출력이 깨끗한가(오류/경고 없음)

**실패한다면?** 테스트가 아니라 코드를 고친다.

**다른 테스트가 깨졌다면?** 지금 바로 고친다.

### REFACTOR — 정리

GREEN 상태에서만 진행한다:
- 중복 제거
- 이름 개선
- 보조 함수 추출
- §6 품질 지표(라인수/복잡도/중복/주석비율/네이밍) 확인 및 위반 수정

테스트는 계속 GREEN을 유지해야 하며, 이 단계에서 새 동작을 추가하지 않는다.

### 반복

다음 기능/계약을 위한 다음 실패 테스트로 넘어간다.

## 2. 좋은 테스트

| 품질 | 좋음 | 나쁨 |
|---|---|---|
| **최소성** | 한 가지만 검증. 이름에 "그리고"가 들어가면 분리한다 | `test_이메일과도메인과공백을검증한다` |
| **명확성** | 이름이 동작을 설명한다 | `test_케이스1` |
| **의도 표현** | 원하는 API를 그대로 보여준다 | 코드가 어떻게 동작해야 하는지 가린다 |

테스트를 작성하거나 수정할 때는 `references/writing-good-tests.md`를 함께 읽는다 — 테스트가
정직한지 지키는 규칙:
- 테스트를 작성하기 **전에** "이 테스트를 실패시킬 프로덕션 변경"이 무엇인지 이름 붙인다
- 모의 객체의 동작이 아니라 실제 동작을 검증한다
- 테스트 전용 코드는 테스트 유틸리티에 두고, 프로덕션 클래스에 넣지 않는다
- 의존성을 모의 처리하기 전에 그 의존성의 부작용을 먼저 이해한다

## 3. 흔한 합리화와 반박

| 핑계 | 실제로는 |
|---|---|
| "너무 간단해서 테스트할 필요 없다" | 간단한 코드도 깨진다. 테스트는 30초면 된다 |
| "나중에 테스트하겠다" | 나중에 작성한 테스트는 바로 통과한다 — 아무것도 증명하지 못한다. 잘못된 것을 검증하거나, 구현을 검증하거나, 잊어버린 경계 케이스를 놓칠 수 있다. 실패를 본 적이 없으니 버그를 잡을 수 있다는 것도 증명한 적이 없다 |
| "선 테스트/후 테스트나 목적은 같다(형식이 아니라 정신이 중요하다)" | 후행 테스트는 "이 코드가 무엇을 하는가"에 답하고, 선행 테스트는 "이 코드가 무엇을 해야 하는가"에 답한다. 후행 테스트는 이미 작성한 코드에 편향되어 기억나는 케이스만 검증한다 |
| "이미 수동으로 테스트했다" | 수동 테스트는 임시방편이다 — 무엇을 검사했는지 기록이 없고, 코드가 바뀌어도 재실행할 수 없으며, 압박 속에서 케이스를 빠뜨리기 쉽다 |
| "지금까지 쓴 시간이 아깝다" | 매몰비용 오류다 — 그 시간은 이미 쓴 것이다. 진짜 선택은 TDD로 다시 쓰는 것(신뢰 가능)과 신뢰할 수 없는 코드를 유지하며 나중에 테스트를 덧붙이는 것(버그 가능성 높음) 중 하나다 |
| "참고용으로 남기고 테스트부터 작성하겠다" | 결국 그 코드를 손보게 된다. 그것은 후행 테스트다. 삭제는 삭제다 |
| "먼저 탐색이 필요하다" | 좋다. 탐색 코드는 버리고 TDD로 다시 시작한다 |
| "테스트하기 어려운 건 설계가 불명확해서다" | 테스트가 하는 말을 들어라 — 테스트하기 어려우면 사용하기도 어렵다 |
| "TDD는 느리다" | TDD가 실용적인 길이다 — 커밋 전에 버그를 잡고, 회귀를 막고, 두려움 없이 리팩터링하게 해준다. "실용적" 지름길은 결국 운영 환경에서 디버깅하는 것이다 |
| "수동 테스트가 더 빠르다" | 수동 테스트는 경계 케이스를 증명하지 못한다. 변경할 때마다 다시 테스트해야 한다 |
| "기존 코드에는 테스트가 없다" | 지금 개선하고 있으니, 기존 코드에도 테스트를 추가한다 |

## 4. 위험 신호 — 발견하면 멈추고 다시 시작

- 테스트보다 코드를 먼저 작성함
- 구현 후 테스트를 작성함
- 테스트가 바로 통과함
- 왜 테스트가 실패했는지 설명할 수 없음
- 테스트를 "나중에" 추가함
- "이번만"이라고 합리화함
- "이미 수동으로 테스트했다"
- "후행 테스트도 같은 목적을 달성한다"
- "형식이 아니라 정신이 중요하다"
- "참고용으로 남기겠다" 또는 "기존 코드를 손보겠다"
- "이미 X시간을 썼으니 지우는 건 아깝다"
- "TDD는 교조적이다, 나는 실용적으로 하고 있다"
- "이번 경우는 다르다..."

**위 항목은 모두 다음을 의미한다: 코드를 삭제하고 TDD로 다시 시작한다.**

## 5. 예시 — 버그 수정 (Python/unittest)

**버그**: 빈 이메일이 그대로 통과됨

**RED**
```python
class TestSubmitForm(unittest.TestCase):
    def testRejectsEmptyEmail(self):
        """
        \\brief 이메일이 빈 문자열이면 "이메일 필수" 오류를 반환하는지 검증한다.
               (프로덕션 코드에서 빈 값 검사를 제거하면 이 테스트는 실패해야 한다)
        \\technique 동등분할 (유효하지 않은 입력 클래스)
        \\testtype 부정 (Negative)
        """
        result = submitForm({"email": ""})
        self.assertEqual(result["error"], "이메일 필수")
```

**Verify RED**
```
$ python -m unittest
FAIL: 'Email required' 예상, 실제 반환값 None
```

**GREEN**
```python
def submitForm(data):
    email = data.get("email", "").strip()
    if not email:
        return {"error": "이메일 필수"}
    # ...
```

**Verify GREEN**
```
$ python -m unittest
OK
```

**REFACTOR**: 여러 필드를 검증해야 한다면 검증 로직을 보조 함수로 추출한다(§6 품질 지표 확인 포함).

## 6. 프로젝트 품질 지표 (CLAUDE.md 구현 지침)

리팩터링 단계와 완료 전 검토에서 아래를 실제로 측정해서 확인한다(추측 금지). 상세 기준과 도구는
`references/quality-metrics-tools.md`, 네이밍은 `references/naming-convention.md`, Doxygen 형식은
`references/doxygen-comment-guide.md` 참고.

| 지표 | 기준 |
|---|---|
| 함수 순수 코드 라인수 | 50줄 이하 |
| 함수 순환복잡도 | 10 이하 |
| 중복 코드 | 7줄까지 허용 |
| 주석 비율(Doxygen) | 전체의 20% 이상 |
| 함수명·변수명 | 3글자 이상, 낙타 표기법(camelCase) |

## 7. 테스트 문서화 규칙 (Doxygen 목적 설명 · 기법 · 긍정/부정 케이스)

모든 테스트 함수(메서드)는 프로덕션 함수와 동일하게 Doxygen 형식 docstring을 가져야 하며, 아래 세
가지를 반드시 포함한다. 상세 규칙과 기법 목록, 더 많은 예시는 `references/test-documentation-guide.md`
참고.

1. **`\brief`(목적 설명)**: 이 테스트가 무엇을 검증하는지, 그리고 "어떤 프로덕션 변경이 있으면 이
   테스트가 실패해야 하는지"를 한 문장으로 적는다(§2 "Name the Break" 원칙과 동일).
2. **`\technique`(사용한 기법)**: 동등분할, 경계값분석, 오류추정, 상태전이 테스트, 결정테이블 테스트,
   버그 재현(회귀) 테스트 등 이 테스트를 설계한 기법을 명시한다.
3. **`\testtype`(긍정/부정 케이스 여부)**: 사전조건을 만족하는 입력에 대한 성공 경로 검증이면
   `긍정(Positive)`, 사전조건 위반·예외·오류·경계 초과 등 실패 경로 검증이면 `부정(Negative)`으로
   표시한다.

이 세 항목은 테스트 코드 자체와 §6의 주석 비율(20% 이상) 산정에 모두 포함된다 — 형식적으로 채우지
않고, 실제로 무엇을 검증하는지 설명하는 내용으로 작성한다.

## 8. 상세설계 정합성 및 SBOM

- 구현하는 함수의 시그니처, 사전조건/사후조건, 예외 처리는 상세설계서의 함수 계약과 일치해야 한다.
  구현 중 계약을 바꿔야 할 필요가 발견되면, 먼저 상세설계서 갱신을 사용자에게 제안하고 구현 코드만
  몰래 다르게 만들지 않는다.
- 외부(오픈소스) 라이브러리를 실제로 사용하면, `WP_Templates/Engineering/
  SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_Python 의존성 SBOM FOSS 라이선스 목록
  템플릿.xlsx` 형식으로 패키지·버전·의존성 유형·SPDX 라이선스·근거 위치를 기록한다.

## 9. 완료 전 체크리스트

- [ ] 새로 작성한 모든 함수/메서드에 테스트가 있는가
- [ ] 구현 전에 각 테스트가 실패하는 것을 직접 확인했는가
- [ ] 각 테스트가 예상한 이유로 실패했는가(기능 없음, 오타 아님)
- [ ] 각 테스트를 통과시키는 최소한의 코드를 작성했는가
- [ ] 모든 테스트가 통과하는가
- [ ] 출력이 깨끗한가(오류/경고 없음)
- [ ] 실제 코드를 사용했는가(불가피한 경우에만 모의 객체)
- [ ] 경계 케이스와 오류 케이스를 다뤘는가
- [ ] 모든 테스트 함수에 Doxygen `\brief`/`\technique`/`\testtype`을 작성했는가 (§7)
- [ ] 함수 순수 코드 라인수 ≤50, 순환복잡도 ≤10, 중복코드 ≤7줄, 주석비율 ≥20%인가 (도구로 측정, §6)
- [ ] 함수/변수명이 3글자 이상이고 camelCase인가
- [ ] 외부 라이브러리 사용 시 SBOM에 기록했는가

체크박스를 모두 채울 수 없다면 TDD를 건너뛴 것이다 — 다시 시작한다.

## 10. 막혔을 때

| 문제 | 해결 |
|---|---|
| 테스트를 어떻게 작성할지 모르겠다 | 원하는 API를 그대로 적는다. 단언(assert)부터 작성한다. 필요하면 사용자에게 확인한다 |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡한 것이다. 인터페이스를 단순화한다 |
| 모든 것을 모의 처리해야 한다 | 코드가 너무 결합되어 있다. 의존성 주입을 사용한다 |
| 테스트 준비(setup)가 거대하다 | 보조 함수로 추출한다. 그래도 복잡하면 설계를 단순화한다 |

## 11. 디버깅과의 연계

버그를 발견하면, 그 버그를 재현하는 실패 테스트부터 작성한다. 그다음 TDD 사이클을 따른다. 테스트가
수정을 증명하고 회귀를 막는다. 테스트 없이 버그를 고치지 않는다.

## 12. 최종 규칙

```
프로덕션 코드 → 테스트가 존재하고 먼저 실패했어야 한다
그렇지 않다면 → TDD가 아니다
```

사용자의 명시적 허락 없이는 예외를 두지 않는다.
