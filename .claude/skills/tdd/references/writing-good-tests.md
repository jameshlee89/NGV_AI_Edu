# 좋은 테스트 작성하기

> 출처: [obra/superpowers](https://github.com/obra/superpowers)
> `skills/test-driven-development/writing-good-tests.md`(MIT License)를 한국어로 번역·각색.

**이 문서를 참고할 시점**: 테스트를 작성/수정할 때, 모의 객체(mock)를 추가할 때, 테스트용 정리(cleanup)/
보조 메서드를 추가할 때.

## 개요

테스트는 특정한 결함을 잡기 위해 존재한다. 다음 두 원칙이 모든 것을 지배한다.

```
1. 모든 테스트는 자신이 잡는 결함(break)의 이름을 댈 수 있어야 한다
2. 모든 테스트는 실제 대상(real thing)을 실행해야 한다
```

엄격한 TDD는 이 둘을 자연스럽게 만족시킨다 — 먼저 작성되어 실제 코드에 대해 실패하는 것을 확인한
테스트는 이미 "실패할 수 있음"을 증명한 것이고, 실제 의존성이 느리거나 외부적이라고 판명될 때만 모의
객체를 쓸 자격을 얻는다.

## 원칙 1: 깨지는 지점에 이름 붙이기

테스트 본문을 작성하기 전에 답한다: **어떤 프로덕션 변경이 이 테스트를 실패시켜야 하는가 — 그리고
그 변경은 버그인가, 의도적 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계
케이스, 깨진 계약 중 하나를 잡을 때 존재 가치를 갖는다.

**기대값은 독립적으로 도출한다.** 리터럴 값과 손으로 확인한 픽스처를 사용한다 — 리터럴 `want` 값을
쓰는 테이블 기반 테스트가 선호되는 형태다. 테스트 대상 코드(또는 그 보조 함수)로 계산한 기대값은
그 코드가 무엇을 하든 항상 통과한다.

```python
# ❌ 거울 단언(mirror assertion): 같은 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# ✅ 손으로 도출한 리터럴
assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기(change detector)를 만들지 않는다.** 의도적인 결정(상수 값, 정확한 메시지 문구, 내부
구조)만 실패시킬 수 있는 테스트는 리팩터링에는 반응하고 버그는 그냥 지나친다. 그 결정에 의존하는
동작을 검증한다 — `assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출은 5번 재시도되고, 6번째
시도는 일어나지 않는다"를 검증한다.

**텍스트가 아니라 동작을 검증한다.** 스크립트, 스킬, 설정 파일이 특정 줄을 포함하는지 검증하는 것은
그 소스가 소스라는 것만 증명한다. 통제된 입력으로 스크립트를 실제 실행하고 출력, 부작용, 종료 코드를
검증한다.

**프레임워크가 아니라 우리 코드를 검증한다.** 코드의 경계에서 우리 코드가 맺는 계약(등록하는 라우트,
발행하는 쿼리, 생성하는 페이로드)을 검증한다. 상위(upstream) 라이브러리의 내부 동작은 그 라이브러리
유지관리자가 테스트할 몫이다(대표적인 예: 라우터가 등록된 핸들러를 호출하는지 검증하는 것 — 그것은
프레임워크의 테스트이지 우리 테스트가 아니다). 상위 동작이 실제로 우리를 놀라게 했다면, 그 가정을
명시한 좁은 범위의 특성화(characterization) 테스트 하나만 작성한다. 생성자, getter, 상수, 단순
위임(forwarding)도 마찬가지다 — 검증/정규화/기본값 설정/도출/강제/부작용 중 하나를 수행할 때만
테스트할 가치가 있고, 그렇지 않으면 그것에 의존하는 첫 번째 관찰 가능한 결과를 검증한다.

### 게이트 함수

```
테스트 본문을 작성하기 전에:
  이 테스트를 실패시킬 프로덕션 변경을 이름 붙인다.

  이름 붙일 수 없다 → 관찰 가능한 동작 중심으로 다시 설계한다
  "소스 텍스트가 바뀌었다" → 그 산출물을 실행하고 효과를 검증한다
  의도적 결정만 잡는다 → 변경 감지기다. 그 결정에 의존하는 동작을 검증한다

  기대값이 테스트 대상 코드 없이 도출되었는지 확인한다.
  테스트 대상 코드나 그 보조 함수를 재사용한다면:
    리터럴 값이나 손으로 확인한 픽스처로 교체한다
```

## 원칙 2: 실제 대상을 실행하기

**모의 객체는 그 자체로는 아무것도 증명하지 않는다.** 모의 객체 존재 여부를 검증하는 단언은 모의
객체가 있을 때 통과하고 없을 때 실패할 뿐, 실제 컴포넌트에 대해서는 아무것도 말해주지 않는다. 실제
컴포넌트의 동작을 검증한다 — 검증하려는 대상이 모의 객체라면, 모의 처리를 풀거나 그 단언을
삭제한다.

```python
# ✅ 실제 동작 검증
self.assertTrue(response.header_exists("navigation"))

# ❌ 모의 객체 존재만 검증
self.assertTrue(sidebar_mock.was_called)
```

**동료의 지적**: "이거 모의 객체의 동작을 테스트하고 있는 건 아닌가요?"

**적절한 수준에서 모의 처리한다.** 실제 메서드의 모든 부작용을 먼저 파악한 뒤, 느리거나 외부적인
연산만 모의 처리하고 테스트가 실제로 의존하는 부분은 그대로 둔다. 확신이 없으면 먼저 실제 구현으로
테스트를 돌려보고 실제로 무슨 일이 일어나는지 관찰한다.

```python
# ❌ 모의 객체가 중복 감지 로직이 읽는 설정 저장 동작까지 삼켜버림
patch("ToolCatalog.discoverAndCacheTools", return_value=None)

# ✅ 느린 서버 기동만 모의 처리, 설정 저장은 실제 동작 유지
patch("MCPServerManager")
```

**더블(double)을 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단언한다 —
무엇이든 받아주는 가짜 객체는 아무것도 검증하지 못한다. 각 분기(성공, 오류, 잘못된 형식)마다 별도의
픽스처나 스파이를 둬서, 잘못된 분기가 기대를 만족시키지 못하게 한다.

**실제 데이터를 완전히 반영한다.** 실제로 존재하는 전체 구조를 모의 처리한다 — 테스트가 읽는
필드만이 아니라 문서화된 모든 필드를. 부분적인 모의 객체는 후속 코드가 누락된 필드를 읽을 때 조용히
실패한다 — 테스트는 통과하는데 통합 환경에서는 깨진다.

**프로덕션 클래스에는 프로덕션 메서드만 둔다.** 테스트만 필요로 하는 정리(cleanup) 코드는 테스트
유틸리티에 두고, 프로덕션 클래스의 `destroy()` 같은 메서드로 만들지 않는다. 자문한다: 이 메서드는
테스트에서만 호출되는가? 이 클래스가 이 자원의 생명주기를 소유하는가? 답이 "아니오"라면 테스트
유틸리티로 옮긴다.

**복잡한 모의 객체보다 실제 컴포넌트를 선호한다.** 모의 객체 준비 코드가 테스트 로직보다 커지거나,
모의 객체에 실제 컴포넌트가 가진 메서드가 빠져 있거나, 모의 객체가 바뀔 때마다 테스트가 깨진다면
실제 컴포넌트를 사용하는 통합 테스트로 전환한다. **자문**: "여기서 정말 모의 객체가 필요한가?"

### 게이트 함수

```
모의 객체나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 부분은 실제로 유지한다.
  느리거나 외부적인 수준만 모의 처리한다.

  모의 응답이 실제 구조를 완전히 반영하는가.

  테스트에서만 호출되는 메서드는 프로덕션이 아니라 테스트 유틸리티에 둔다.

  모의 객체 자체를 검증하려는 것은 아닌가?
    모의 처리를 풀거나 그 단언을 삭제한다.
```

## 테스트는 구현과 함께 완성된다

TDD 사이클 — 실패하는 테스트, 최소 구현, 리팩터링 — 이 곧 "완료"의 의미다. 그 동작이 필요로 하는
테스트만 남긴다 — 사소한 코드와 사람이 읽는 문서는 테스트가 필요 없고, 절차를 만족시키기 위해서만
작성한 테스트는 영원히 유지보수 비용만 발생시킨다.

## 뮤테이션 점검 (Mutation Check)

마무리하기 전에, 머릿속으로 프로덕션 코드를 조금씩 바꿔본다(뮤테이션). 현실적인 뮤테이션 각각에
대해 적어도 하나의 테스트가 실패해야 한다.

- 잘못된 상수나 인자
- 잘못된 분기 처리
- 누락된 상태 변화나 부작용
- 빈 값이나 기본값 반환
- 0, 빈 값, None, 미인가, 잘못된 형식 입력에 대한 검증 누락

어떤 뮤테이션도 잡지 못한다면 그 동작은 보호되지 않은 것이거나, 테스트가 항상 참(tautological)인
것이다.

## 빠른 참조

| 상황 | 할 일 |
|---|---|
| 테스트를 작성할 때 | 잡으려는 결함(버그이지 결정이 아님)에 이름을 붙인다 |
| 기대값을 만들 때 | 손으로 도출한다 — 테스트 대상 코드로 계산하지 않는다 |
| 스크립트/문서를 테스트할 때 | 실행하거나 사용하는 쪽을 압박 테스트한다 — 텍스트를 grep하지 않는다 |
| 의존성 테스트를 만들고 싶을 때 | 그들이 문서화한 내부 동작이 아니라 우리 경계 계약을 검증한다 |
| 모의 처리된 요소를 검증하고 싶을 때 | 실제 컴포넌트를 검증하거나 모의 처리를 푼다 |
| 메서드를 모의 처리하려 할 때 | 부작용을 먼저 파악하고, 느리거나 외부적인 수준만 모의 처리한다 |
| 모의 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트에서만 쓰는 정리 코드가 필요할 때 | 테스트 유틸리티에 둔다 |
| 모의 객체 준비 코드가 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 완성했을 때 | 뮤테이션 점검을 수행한다 |

## 경고 신호

- 준비(setup)와 단언(assertion)이 같은 객체를 공유해서 항상 같음이 보장됨
- 패닉, 크래시, 셀렉터 누락으로만 테스트가 실패할 수 있음
- 의도적인 변경마다 실패하고, 실수로 인한 결함에는 절대 반응하지 않음
- 기대값이 반복문, 빌더, 헬퍼 뒤에 숨겨져 있음
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인함
- 프레임워크만 남아도 여전히 의미가 있는 테스트임
- 부작용이나 결과 확인 없이 커버리지만을 위해 존재함
- `*-mock` 테스트 ID를 검증하거나, 모의 객체를 제거하면 실패함
- 어떤 메서드가 테스트 파일에서만 호출됨
- 모의 객체 준비 코드가 테스트의 절반 이상을 차지하거나, 왜 필요한지 설명할 수 없음
- "혹시 몰라서" 모의 처리함
