# SW 시스템 테스트 케이스 생성

## 개요

SW 요구사항 명세서 기반으로 SW 시스템 테스트 케이스를 생성하기 위한 방법론 스킬입니다. 이 스킬은 "무엇을 근거로, 어떤 기법으로, 어떤 원칙으로" 테스트 케이스를 설계할지에 대한 방법론만 정의합니다. 요구사항 분석, 사용자와의 확인, 실제 산출물(xlsx) 작성은 이 스킬을 사용하는 에이전트(예: `sw-system-tester` 서브에이전트)가 수행합니다.

## 적용 범위와 인접 스킬과의 경계

이 스킬은 **SW 요구사항 명세서를 근거로 한 블랙박스 기능/비기능 시스템 시험**(A-SPICE SWE.6 성격)만
다룬다. 아래 항목은 이 스킬이 담당하지 않으며, 필요하면 해당 스킬을 사용하도록 안내한다.

| 대상이 아닌 것 | 담당 스킬 |
|---|---|
| 함수/모듈 단위의 화이트박스 테스트, 코드 품질 지표 | `tdd` |
| 아키텍처 설계서의 인터페이스·통합 순서에 근거한 통합시험, 함수/Call 커버리지 | `integration-testing` |
| 요구사항 자체의 도출/명세, 추적성 매트릭스 관리 | `requirements-analyst` |

이 스킬의 테스트 케이스는 **코드 구조가 아니라 SW 요구사항 명세서**를 유일한 근거로 삼는다 —
소스 코드의 커버리지(라인/함수/Call 등 구조적 커버리지)를 목표로 케이스를 만들지 않는다(그 책임은
`tdd`·`integration-testing`에 있다).

## 기반지식

- **ISO 26262 Part 6**: 소프트웨어 시스템/자격인정 시험(system/qualification test) 수준에서 요구되는
  블랙박스 시험 원칙. 특히 ASIL 등급이 할당된 요구사항은 판정기준의 경계값·조건 조합을 빠짐없이
  검증해야 합니다. (단위/통합 수준의 화이트박스 시험·구조적 커버리지 요건은 이 스킬이 아니라
  `tdd`/`integration-testing` 스킬이 다룹니다.)
- **A-SPICE SWE.6**: 소프트웨어 시스템 시험(자격인정 시험)에 대한 Base Practice. SW 요구사항과 시험
  케이스 간 양방향 추적성과 표준화된 시험 절차를 요구합니다. (SWE.4 단위 검증은 `tdd`, SWE.5 통합
  시험은 `integration-testing` 스킬이 다룹니다.)
- **ISO 29119 및 ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의
  근거로 사용합니다.
- **ISO 25000 (SQuaRE)**: 비기능(품질) 요구사항을 분류하는 기준입니다. 비기능 테스트 케이스는 이 표준의
  품질 특성(예: 기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별로
  그룹화합니다.

## 적용 대상 테스트 기법

요구사항의 성격에 맞춰 아래 기법 중에서 선택하여 적용하고, 각 테스트 케이스의 "사용 기법" 항목에 실제로
적용한 기법을 명시합니다. 각 기법의 상세 설명·예시는 `references/test-design-techniques.md` 참고 —
이 파일이 이 저장소 전체에서 이 기법들(경계값분석/동등분할/오류추정 등)을 정의하는 단일 기준이며,
`tdd`·`integration-testing` 스킬은 이 파일을 참조하고 자체 정의를 반복하지 않는다.

- **경계값 분석(Boundary Value Analysis)**: 경계값 미만/경계값/경계값 초과를 각각 별도 케이스로 도출
- **동치 클래스(Equivalence Partitioning)**: 입력 도메인을 유효/무효 클래스로 나누어 대표값 도출
- **조합 테스트(전 조건 조합)**: 조건 수가 적어 전수 조합이 실행 가능할 때 우선 적용
- **페어와이즈**: 조합 수가 많아 전수 조합이 비현실적일 때 대체 적용
- **엣지 케이스**: 정상 범위의 극단, 동시성/타이밍 등 특이 조건
- **경험 기반 테스트(오류 추정/탐색적 테스트)**: 결함 이력이나 QA 경험에 근거한 오류 추정

## 작성 원칙

- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 생성하지 않습니다.
- 테스트의 예상 결과를 임의로 가정하지 않습니다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받아야 합니다.
- 프로젝트에서 정한 테스트 커버리지 목표(예: CLAUDE.md에 명시된 기준)를 준수합니다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성합니다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받습니다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분합니다.
- 사용한 테스트 설계 기법을 각 케이스에 명시합니다.

## 도구 사용

- 페어와이즈 조합을 생성할 때는 오픈소스인 PICT를 사용합니다.
- 전수 조합(모든 조건의 조합)을 생성할 때는 PICT의 `/o:max` 옵션을 사용합니다.

## 산출물 구조

회사 지정 템플릿(TPL-SWE6-001 검증 명세서, TPL-SWE6-002 검증 결과서)이 `WP_Templates/Engineering/
SoftwareVerification/`에 있다 — 상세 열 구성은 `references/template-source.md` 참고. 이 스킬은 그
템플릿의 핵심 열(Test ID, SW Req, Stimulus, Expected Result, Technique 등)을 유지하면서, 기능/비기능을
분리해 관리하는 아래 관례를 추가로 적용한다.

- 기능 요구사항에 대한 테스트 케이스: "테스트 케이스" 시트
- 비기능 요구사항에 대한 테스트 케이스: 별도의 "비기능 테스트 케이스" 시트, ISO 25000 품질 특성별로 구분
- 요구사항 원문에 없거나 원문보다 엄격하게 사용자 확인을 거쳐 확정한 판정기준: "확정 근거" 열에 확정 일자와 승인 주체 기록
- 템플릿에 없는 열(사전조건, 절차, 우선순위 등)을 추가로 쓰는 경우, 템플릿의 필수 열은 그대로 유지한
  채 확장한다.
