# 통합 순서 기반 단계적 시험 진행 가이드

SKILL.md §4에서 사용한다. `architecture-design` 스킬의 `integration-order-guide.md`로 정의된 통합
순서를 시험 실행 계획으로 그대로 옮긴다 — 이 스킬 단계에서 순서를 새로 만들지 않는다.

## 1. 기본 원칙

- 아키텍처 설계서(TPL-SWE2-001 11장)에 정의된 통합 순서(단계, 각 단계의 통합 대상 컴포넌트, 필요한
  스텁/드라이버, 검증 대상 인터페이스)를 그대로 시험 계획의 뼈대로 사용한다.
- 통합 순서가 아키텍처 설계서에 없거나 불명확하면, 먼저 `architecture-design` 스킬로 통합 순서를
  정의하도록 사용자에게 제안한다 — 이 스킬에서 임의로 순서를 만들지 않는다.

## 2. 각 단계에서 수행할 것

아키텍처의 통합 순서표(단계 번호, 통합 대상 컴포넌트, 필요한 스텁/드라이버, 검증 대상 인터페이스,
회귀 범위, 완료 기준) 각 행에 대해 다음을 수행한다.

1. **환경 구성**: 이번 단계까지 실제 구현체로 통합된 컴포넌트와, 아직 구현되지 않은 의존 대상을
   대신할 스텁/드라이버를 구성한다(템플릿 4장 환경 및 형상).
2. **시험 케이스 실행**: 이 단계에서 검증할 인터페이스(`IF-XXX`)에 대응하는 통합시험 케이스(§6)를
   실행한다.
3. **진입/종료 기준 확인**: 템플릿 5장에 정의한 이 단계의 종료 기준(케이스 통과율, 커버리지 등)을
   만족하는지 확인한다.
4. **커버리지 확인**: 이 단계 범위 내 함수/Call 커버리지를 측정한다(§5, `coverage-measurement-
   guide.md`). 이번 단계에서 새로 통합된 부분이 커버되지 않았으면, 다음 단계로 진행하기 전에 케이스를
   보강한다.
5. **회귀 확인**: 이전 단계까지 통과했던 케이스가 이번 단계 통합으로 영향을 받지 않았는지 확인한다
   (템플릿 9장 회귀 전략).
6. **결과 기록**: TPL-SWE5-003 형식으로 이번 단계 실행 결과를 기록한다.

## 3. 안전 관련(ASIL) 단계 처리

아키텍처 설계서에서 오류 격리/안전 상태가 정의된 인터페이스가 이번 단계에 포함되면, 결함주입시험
(`iso26262-integration-test-techniques.md` §1)으로 그 메커니즘이 실제로 동작하는지 반드시 이 단계에서
검증한다 — 나중 단계로 미루지 않는다.

## 4. 순서를 지키지 못하는 경우

- 실제 구현 진행 상황(어떤 컴포넌트가 아직 구현되지 않음) 때문에 계획된 순서대로 진행할 수 없으면,
  임의로 다른 순서로 진행하지 않고 사용자에게 상황을 알린 뒤 스텁으로 대체하거나 순서 조정 필요성을
  아키텍처 설계서 갱신과 함께 논의한다.
