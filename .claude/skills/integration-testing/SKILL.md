# 통합시험자

이 스킬은 A-SPICE(SWE.5)와 ISO 26262 Part 6에 따라 소프트웨어 통합시험을 설계·실행하고, 회사 지정
양식으로 산출물을 작성하는 절차와 규칙을 제공한다. 목표는 다음 요건을 모두 만족하는 통합시험
산출물을 만드는 것이다.

1. 지정된 템플릿(TPL-SWE5-001/002/003) 준수
2. 아키텍처 설계서(SWE.2)의 **인터페이스**와 **통합 순서**를 시험 베이시스로 사용
3. ISO 26262 Part 6에 근거한 시험기법 적용
4. **함수 커버리지 100%, Call 커버리지 100%** 실제 측정 및 달성
5. 통합 순서에 따른 단계적(incremental) 시험 진행
6. 실행 결과·결함·회귀 범위의 양방향 추적성 확보

## 적용 범위와 인접 스킬과의 경계

이 스킬은 **아키텍처 설계서의 인터페이스와 통합 순서에 근거한 통합시험**(A-SPICE SWE.5 성격,
화이트/그레이박스, 구조적 커버리지 포함)만 다룬다. 아래 항목은 이 스킬이 담당하지 않는다.

| 대상이 아닌 것 | 담당 스킬 |
|---|---|
| SW 요구사항 명세서 기반 블랙박스 기능/비기능 시스템 시험 (코드 커버리지 목표 없음) | `sw-system-test` |
| 함수/모듈 단위의 화이트박스 테스트(TDD), 코드 품질 지표 | `tdd` |
| 아키텍처/상세설계 자체의 작성 | `architecture-design` / `detailed-design` |

이 스킬의 시험 케이스는 **아키텍처 인터페이스와 통합 순서**를 유일한 근거로 삼는다 — SW 요구사항
명세서를 직접 근거로 한 블랙박스 케이스 설계는 `sw-system-test` 스킬의 역할이다.

## 0. 시작할 때 항상 할 일

1. `references/template-source.md`를 읽는다. 회사 지정 템플릿(TPL-SWE5-001 docx, TPL-SWE5-002/003
   xlsx)이 이미 저장소에 있으므로, 이 SKILL.md의 장 구성을 그대로 목차로 사용해 작성한다.
2. **시험 베이시스인 아키텍처 설계서(SWE.2, `architecture-design` 스킬 산출물)를 먼저 확인한다.**
   인터페이스 명세(TPL-SWE2-001 6장)와 통합 전략/순서(11장)를 읽는다. 찾을 수 없으면 사용자에게
   위치를 확인한다 — 아키텍처 근거 없이 임의로 통합시험 범위/순서를 정하지 않는다.
3. 상세설계서(SWE.3)와 실제 구현 코드(`detailed-design`/`tdd` 스킬 산출물)를 찾아, 실제 함수 목록과
   호출관계를 확인한다 — §5 커버리지 측정의 기준 집합을 만드는 데 필요하다.
4. Python 인터프리터와 커버리지 측정에 필요한 도구(`coverage` 패키지 등, `references/
   coverage-measurement-guide.md` 참고)가 실제로 설치되어 있는지 확인한다. 없으면 설치 여부를
   사용자에게 먼저 확인한다 — 도구 없이 "커버리지를 달성했다"고 단정하지 않는다.

## 2. 시험 베이시스 — 아키텍처 인터페이스와 통합 순서 (필수 선행 단계)

통합시험은 상세설계나 구현 코드를 보고 임의로 케이스를 만드는 것이 아니라, **아키텍처 설계서를
시험 베이시스로 삼아** 다음을 먼저 확정한다.

- [ ] 아키텍처 설계서의 인터페이스(`IF-XXX`) 목록을 모두 나열했는가 — 각 인터페이스는 최소 1개 이상의
      통합시험 케이스로 커버되어야 한다(§6).
- [ ] 아키텍처 설계서의 통합 전략(통합 항목 ID, 선행조건, 의존성, 순서)을 그대로 옮겨왔는가 — 새로운
      통합 항목이나 순서를 이 스킬 단계에서 임의로 추가/변경하지 않는다. 변경이 필요하면 먼저
      아키텍처 설계서 갱신을 사용자에게 제안한다.
- [ ] 각 통합 항목이 검증하는 아키텍처 요소(`ARC-XXX`)와 인터페이스(`IF-XXX`)가 명확히 연결되는가.

## 3. ISO 26262 Part 6 근거 시험기법

`references/iso26262-integration-test-techniques.md`에 상세 목록과 원문 대조 필요 사항이 있다. 요약:

- **시험 방법(무엇을 시험할지)**: 요구사항기반시험(아키텍처/SW 요구사항으로부터 도출), 인터페이스시험
  (컴포넌트 간/외부 인터페이스가 계약대로 동작하는지), 결함주입시험(오류 주입 시 오류 격리/안전 동작이
  설계대로 동작하는지, ASIL 대상에 특히 중요), 자원사용시험(메모리/CPU/통신 자원 사용이 설계 범위
  내인지), 필요 시 백투백비교시험(모델과 코드 비교, 해당하는 경우).
- **시험 케이스 도출 기법(어떻게 케이스를 만들지)**: 동등분할, 경계값분석, 오류추정. `detailed-design`
  스킬의 함수 계약(사전/사후조건, 경계값)을 그대로 케이스 설계 입력으로 사용한다.
- 정확한 표 번호·문구·ASIL별 권고 수준은 이 요약만으로 단정하지 말고, 프로젝트에 첨부된 공식 ISO
  26262 Part 6 문서로 확인한다. 이 프로젝트는 사용자 지시에 따라 ASIL 권고 수준과 무관하게 **함수/Call
  커버리지 100%를 항상 목표로 한다**(§5).

## 4. 통합 순서에 따른 단계적 시험 진행

`references/staged-integration-guide.md`에 상세 절차가 있다. 핵심 규칙:

- 아키텍처 설계서(§2)에 정의된 통합 순서를 그대로 따라 단계를 진행한다. 순서를 바꾸거나 여러 단계를
  한꺼번에 합쳐서 시험하지 않는다.
- 각 단계마다: 이번에 새로 통합되는 컴포넌트, 필요한 스텁/드라이버, 검증할 인터페이스와 시나리오,
  진입/종료 기준(템플릿 5장), 완료 후 회귀 범위를 명시한다.
- 한 단계의 종료 기준(해당 단계 케이스 통과 + 해당 단계 범위의 커버리지 확인)을 만족해야 다음 단계로
  진행한다.
- 안전 관련(ASIL) 인터페이스가 있으면, 그 오류 격리/안전 동작이 실제로 검증되는 단계를 명확히 표시한다
  (아키텍처 설계서의 오류 격리 설계와 일치해야 함).

## 5. 함수 커버리지 · Call 커버리지 100%

`references/coverage-measurement-guide.md`에 측정 스크립트와 도구 사용법이 있다. 핵심 규칙:

- **함수 커버리지**: 통합 대상 소스의 모든 함수가 통합시험 실행 중 최소 1회 이상 호출되어야 한다.
- **Call 커버리지**: 아키텍처 인터페이스(`IF-XXX`)에 대응하는 호출과 상세설계 호출관계에 정의된 모든
  호출 지점(호출자→피호출자 쌍)이 통합시험 실행 중 최소 1회 이상 실제로 실행되어야 한다.
- 두 지표 모두 **실제 실행 후 도구/스크립트로 측정한 값**으로 보고한다 — 추정하거나 "커버할 것"이라고
  단정하지 않는다.
- 100%에 미달하면:
  1. 먼저 커버되지 않은 함수/호출을 실제로 검증하는 통합시험 케이스를 추가한다.
  2. 정말로 통합시험으로 도달할 수 없는 코드(예: 방어적 코드 중 설계상 도달 불가능함이 근거로
     증명된 부분)라면, 임의로 통과 처리하지 말고 사용자에게 확인한 뒤 템플릿 12장(적용 한계)에 사유와
     근거를 명시적으로 기록한다.
- 커버리지 측정 도구가 설치되어 있지 않으면 설치를 사용자에게 안내하고, 설치 전에는 수치를 단정하지
  않는다.

## 6. 통합시험 케이스 작성 (TPL-SWE5-002)

열 구성: `Test ID | Trace | Integration Item | Stimulus | Expected Result | Technique | Automation`

- **Trace**: 이 케이스가 검증하는 아키텍처 인터페이스(`IF-XXX`)/요구사항(`SWR-XXX`) ID.
- **Integration Item**: §4의 통합 항목 ID와 연결.
- **Stimulus/Expected Result**: §3의 기법(동등분할/경계값분석/오류추정 등)으로 도출한 구체적 입력과
  기대 결과. 모호한 표현("정상적으로 동작한다") 대신 검증 가능한 값으로 작성한다.
- **Technique**: §3에서 실제로 사용한 방법/기법명을 기록한다(하나 이상 가능).
- **Automation**: 자동화 여부와 자동화된 경우 실행 방법(예: `python -m unittest <경로>`).
- 자동화된 통합시험을 Python 코드로 작성하는 경우, `tdd` 스킬의 Doxygen 문서화 규칙(`\brief`,
  `\technique`, `\testtype`)을 동일하게 적용해 일관성을 유지한다(§7 참고).

## 7. 실행 및 결과 기록 (TPL-SWE5-003)

열 구성: `Test ID | Trace | Result | Actual Result | Evidence Locator | Defect ID | Disposition`

- 모든 케이스는 실제로 실행한 뒤 결과를 기록한다 — 실행하지 않고 "통과할 것"이라고 단정하지 않는다.
- 실패/편차는 결함 ID와 연결하고, 처리 상태(재시험 예정/수정 완료/보류 등)를 명시한다.
- 실행 요약 시트(Run ID/Date/Baseline/Environment/Planned/Pass/Fail/Overall/Limitation)에 이번 실행의
  전체 판정과 §5에서 확인하지 못한 커버리지 범위(있다면)를 함께 기록한다.

## 8. 회귀 전략

- 코드/인터페이스 변경이 발생하면, 변경된 컴포넌트와 그에 의존하는 컴포넌트(아키텍처의 정적 의존성
  기준)까지 회귀 시험 범위에 포함한다.
- 회귀 시험도 §5의 커버리지 기준(변경 범위 내 함수/Call 100%)을 동일하게 적용한다.

## 9. 추적성

- 아키텍처 인터페이스(`IF-XXX`) ↔ 통합시험 케이스(`Test ID`) ↔ 실행 결과 ↔ 결함(`Defect ID`)이
  양방향으로 연결되어야 한다(템플릿 11·13장).
- 어떤 인터페이스도 시험 케이스 없이 남지 않아야 하고(고아 인터페이스 없음), 어떤 시험 케이스도 근거
  없이 존재하지 않아야 한다(근거 없는 케이스 없음).
- 프로젝트에 추적성 매트릭스가 있으면 같은 작업 안에서 함께 갱신한다.

## 10. 산출물 저장 및 파일명 규칙

- 통합전략/시험명세서(TPL-SWE5-001), 시험 케이스(TPL-SWE5-002), 결과서(TPL-SWE5-003)를 실제로 작성할
  때는 `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/`의 원본
  템플릿을 복사한 뒤, `WP_Templates/Engineering/README.md` 규칙대로 파일명을
  `<산출물 ID>_<산출물명>.<확장자>` 형식으로 바꾸고 프로젝트/베이스라인 정보를 채운다. 저장 위치를
  사용자가 지정하지 않았다면 먼저 확인한다.
- 템플릿 ID·적용 산출물·실제 파일 위치는 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`에
  기록되어 있으므로, 새 산출물을 등록해야 하는지 사용자에게 확인한다.

## 11. 최종 자체 검토 체크리스트

- [ ] 모든 통합시험 케이스가 아키텍처 인터페이스/통합 항목에서 도출되었는가 (§2)
- [ ] 통합 순서를 아키텍처 설계서 그대로 따랐는가, 임의로 순서를 바꾸지 않았는가 (§4)
- [ ] 각 케이스에 ISO 26262 Part 6 기반 기법을 명시했는가 (§3, §6)
- [ ] 함수 커버리지 100%를 실제 도구로 측정해 확인했는가 (§5)
- [ ] Call 커버리지 100%를 실제 도구/스크립트로 측정해 확인했는가 (§5)
- [ ] 100% 미달 항목이 있다면 케이스 보강 또는 사용자 확인 후 "적용 한계"로 문서화했는가 (§5, 템플릿
      12장)
- [ ] 모든 케이스를 실제로 실행하고 결과를 기록했는가 (§7)
- [ ] 실패/편차가 결함과 연결되고 처리 상태가 명시되었는가 (§7)
- [ ] 아키텍처 인터페이스 ↔ 케이스 ↔ 결과 ↔ 결함 추적성에 고아 항목이 없는가 (§9)
- [ ] ISO 26262/A-SPICE 조항을 원문 확인 없이 단정적으로 인용하지 않았는가
